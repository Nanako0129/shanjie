# S2 迭代方法審查（Fable 5.1，effort xhigh，2026-10-03）

以唯讀方式（只用 Read／Glob／Grep）審查 `experiments/s2/` 與相關資料；簡報內容見 commit 訊息。main 已核對其中的詞庫數字（「得」「地」在 ㄉㄜ˙ 下是佔位分數 −6.8、551 個佔位分數、「訬獪」−7.17 對「超」＋「快」−7.50），全部屬實。以下為原文。

**結論。** 我只讀了檔案，沒有執行任何程式。下面的機制是從程式碼和詞庫推得的，預期效益都是估計，不是量測。

迴圈卡住有三個主因，依重要性排列：

1. 評估解析度不夠，accept 規則又是四個集合的零容忍聯集，幾乎沒有變更過得了。
2. bonus 公式混用兩套 unigram，稀有詞、異體字和佔位分數被系統性抬高。這是模型和先驗的問題，加語料解決不了，Round 3 也一樣。
3. 調整集和合成語料都是 LLM 寫的，調整集指不出真實聊天的方向。

搜尋不像主因，但 harness 沒有記加了 bigram 之後的 oracle@64，所以目前無法排除。

## 1. 為什麼卡住

**解析度。** 下表是配對比較達到 5% 顯著所需的淨增益。我假設一次變更會改動 4% 的句子，這個比例要有逐句紀錄才量得到。

| 集合 | 一句的份量 | 需要的淨增益 |
|---|---|---|
| dev 302 | 0.33 百分點 | 約 2.3 |
| typing 76 | 1.32 | 約 4.5 |
| Discord 845 | 0.12 | 約 1.4 |
| 新聞 294 | 0.34 | 約 2.3 |
| 12,500 列 | 0.008 | 約 0.35 |

Round 1 的差距全在雜訊內。0.5 百分點的停止門檻要一萬列以上才分辨得出來。

**Accept 規則丟掉了訊號。** 下表是 `experiments/s2/log.tsv` 相對基準的句數差。

| 設定 | dev | typing | Discord | 新聞 | 結果 |
|---|---|---|---|---|---|
| λ 0.4 | −4 | 0 | +8 | −3 | 拒絕 |
| D 0.9 | 0 | 0 | +2 | +1 | 拒絕 |
| k 3 | −1 | +1 | +4 | 0 | 拒絕 |

Discord 對 λ 和 k 都是單調的。λ 從 0.6 降到 0.4 一路變好，k 從 20 降到 3 也一路變好。targeted 權重從 5 升到 20 則一路變差。最佳點在基準之外，沒有人去找。

## 2. 迭代架構

1. **逐句落地。** 每次 run 把每列的對錯、正解名次、正解與第一名的分數差寫成檔案，私有集合寫到私有目錄。比較工具讀兩個 run，印出修好幾句、弄壞幾句、精確 McNemar 檢定和 paired bootstrap 區間。
2. **錯誤三分。** 對正解做強制解碼，把每個錯句分成到不了、搜尋錯、模型錯。模型錯再標類別：功能詞混淆、內容詞同音、異體字、輸出含 overlay 詞、牽涉佔位分數。
3. **機會表決定下一步。** 每一類算 oracle 上限，也就是把該類全部改對能多幾句。下一個變更選上限乘以把握再除以工時最大的，跑之前先寫下預期會動的類別。
4. **連續指標。** 把 64 名候選的分數做 softmax，取正解的對數損失。它的變異遠小於對錯計數，適合調超參數，top-1 只用來確認。同時記錄 oracle@64 和模型大小，這兩項本來就是 S2 的驗收條件。
5. **資料角色重排。** 從語料切出一到兩萬句不進計數的句子當大調整集，自動標讀音並排除破音字句。Common Voice 是 CC0，那一部分可以進 repo。Discord 請抽取端再抽幾千句使用者自己的訊息當私有調整集，只輸出彙總。抽不到就把 845 列依列號雜湊對半分。dev 302 和 typing 76 降為挑戰集，按類別報告，不當門檻。
6. **Accept 規則。** 主指標在大調整集上配對檢定顯著才進候選。驗證集改成不劣性檢查，退步不超過一個配對標準誤就算過。每累積三到五個候選才看一次驗證集，並記下看過幾次。
7. **速度。** 先分開計時載入和解碼。N0 量到 Python 的 unigram N-best 中位數是每句 6 ms，所以 5 到 8 分鐘可能多半花在載入與合併 pickle，這點未量測。同一組語料在同一個程序裡掃 λ、D 和下限。另外存下 top-256 路徑，參數掃描和 reranker 實驗只需重算分數。語料混合權重用留出文字的 cross-entropy 調，不必解碼。

## 3. 下一步的改動與方法問題

| # | 改動 | 怎麼測 | 成本估計 |
|---|---|---|---|
| 1 | 統一 unigram。backoff 分布改用路徑分數那一套先驗，未見詞一樣吃 backoff 權重，送出時加句尾項，bonus 設下限 | 設定加 `prior`、`eos`、`floor` 三欄。看弄壞的句數、異體字類和 overlay 類。預測 λ 的最佳點會往 1 移動 | 數小時，不花 API |
| 2 | 重估先驗。overlay 分數改由語料頻率決定且只降不升。551 個佔位分數用語料重估，破音字的讀音比例靠建置期的 g2pW 分配。異體字表同時套到語料和詞庫 | 看「的得地」類和 overlay 污染類。調整集有 10 列要在 ㄉㄜ˙ 選出「得」或「地」。規則必須全域適用，不逐詞手調 | 約一天，不花 API |
| 3 | top-64 的線性判別式 reranker。特徵含基礎分、bigram 分、詞數、overlay 詞數，以及混淆字和前後詞的聯合特徵 | 標籤免費：語料句子轉讀音再解碼，正解就是原句。在快取的 N-best 上離線訓練，混淆集清單從大調整集挖。Round 2 的 targeted 句子在這裡才派得上用場 | 兩到四天 |
| 4 | 詞類特徵。用語料做無監督分群，避開詞性資料的授權問題 | 先當 reranker 特徵，看「再」後面接未見動詞的案例 | 兩到三天 |
| 5 | trigram 與更大語料 | 一律在剪枝到 100 MB 之後比較準確率。要先補上 trigram 計數 | 一到兩天，預期增益小 |

改動 3 的模型估計只有幾 MB，每個候選是微秒級，這兩點都未量測。小型神經 reranker 留在 S7。標籤是免費的，不需要 LLM 教師來標註，剩下的 API 預算建議先不動。

**方法問題。**

- **驗證集已經參與選模。** k 是看著 Discord 和新聞的數字挑的，之後每一輪又拿它們當否決條件，見 `experiments/s2/eval_mix.py:27`。
- **合成語料沒有對照組。** README 缺「不含合成句、k 等於 5」那一格，k 和合成句的效果混在一起。
- **k 和 D 不是獨立旋鈕。** 計數先乘 k 再減 D，口語的單次出現等於被當成看過五次，見 `experiments/s2/iterate.py:51`。
- **order 3 會靜默退化成 bigram。** 計數檔沒有 tri，見 `experiments/s2/build_counts.py:162`。
- **log 的 commit 對不上實際的程式和資料。** 工作目錄有未提交的修改，計數檔也沒有記雜湊。
- **「新聞稿贏過內建」不成立。** 59 句對 64 句的差距在雜訊內，設定又是看著新聞數字挑的，只能說打平。
- **`docs/typing-test.md:47` 的診斷有誤。** 它說 ㄉㄜ˙ 下沒有「得」，詞庫其實有，問題是分數。
- **混淆字統計以字計數，且只算等長輸出。** 「嚐嚐」一句算兩次，8 次其實是 4 句，見 `experiments/s2/iterate.py:137`。
- **targeted 清單直接取自 typing 的錯字。** 這批資料的效果不能再用 typing 驗證。錯誤從 4 變 5 只是一句的差別，不能解讀成變差。過濾用的是產生句子的同一個模型，精確度沒量過。
- **前文欄被丟掉。** harness 量不到產品實際會有的左文，見 `experiments/s2/iterate.py:108`。

**建議順序。** 先做逐句落地和比較工具。接著跑改動 1 和 2，它們不花 API，也最可能解除卡住。大調整集和 reranker 排在後面。
