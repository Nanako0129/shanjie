# 長前文評測集（探索片的評測工具，不進 main 的判讀）

起因：P3（前文加長）用的聊天評測集，前文欄只有「同一則訊息的前一串漢字（2～30 字），或 10 分鐘內上一則訊息的最後一串」（`experiments/e2-chateval/build_chatclause.py` 的 `clauses`），量不到 64 字前文的效果。維護者 2026-10-19 晚上在 Discord 提議找散文或公開貼文當長句子的評測，「反正不進訓練我們是拿來打分」，再用選擇題選了：**兩份公開長文都做（HPLT 論壇與部落格、維基文庫散文）**，並且**私人聊天評測集的前文欄一起重建**。

## 登記（2026-10-19，main 寫，建集合之前 commit）

這一片只產生評測集，不訓練、不出貨、不改任何既有判讀。新集合對 P3 只當補充報告；P3 的登記判讀照原集合（`experiments/p3-context/README.md`，PR #228）。

**共同規則**
- 列的格式照現有集合：`前文|句子|讀音`。「句子」是一段連續漢字（`e2common.HAN`：2～30 個漢字），也就是使用者一次打完、按確認的單位。
- **前文**＝同一則訊息（公開長文是同一段落）裡、這段句子開頭之前的原文，依序做三步：(1) `\r`、`\n`、`\t`、`|`、`#` 各換成一個空白（`#` 開頭的行會被 CLI 與 `tools/readings.py` 當註解跳過，L0 曾因此少了 34 列）；(2) 去掉結尾的非漢字（標點、空白、英數）；(3) 取最後 64 個字元。這是 App 前文回傳要給的範圍（`docs/contracts/oc-experimental.md` §0 第 3 點：殼給同一則訊息、跨標點、最多 64 字的前文；B 片才做）。第 (2) 步讓 n-gram 的前文（`context_key`，碰到非漢字就停）和舊欄位一樣看得到上一串漢字。
- 不跨訊息：一則訊息的第一段句子前文是空的（舊欄位會接 10 分鐘內上一則訊息的最後一串，新欄位不接）。
- 每份輸出檔：行數等於報告的列數，每行用 `|` 切開剛好 3 欄，前文欄沒有 `|`、`\r`、`\t`、`#`，沒有任何一行以 `#` 開頭；CLI dump 讀到的列數（摘要行的 `n`）等於輸出檔的行數（A 的三份也等於凍結檔的列數）。不合就停。
- 集合、建置中間檔、分數都放 repo 外（私人的在 `~/side-project/shanjie-private/chat-eval/work-ctx64/`，公開長文在 `~/.cache/shanjie/longctx/`），只回數字與雜湊；原文不進研究紀錄、契約、commit 或 PR。

**A. 私人聊天集合換前文欄**（chatclause、chatjudge、discordtune；chatjudge-2 是確認用的判讀集，不動）

同一批列、同一個正解與讀音（讀音直接取凍結檔的，不重新產生），只換前文欄，新舊才能逐列配對。輸出 `<集合>.ctx64.rows.txt` 與雜湊；報列數、新前文的長度分佈（平均、四分位、空的比例）、和舊前文相同的比例。

- **chatclause、chatjudge**（`chat-eval/work-v2/`，凍結檔 `tune.rows.txt` `81c035b0…`、`chatjudge.rows.txt` `2eb2b6f6…`；不改這個目錄的任何檔）：
  1. 用同一份聊天匯出（`chat-eval/exports/` 的 discord、facebook、threads）、同一個 `--self-name`，在**新的工作目錄** `work-ctx64/` 跑一次和 `prepare` 相同的抽取，但**不給 `--exclude`**，另外替每段句子寫出新前文。不給排除清單的結果，是凍結時 `clauses.tsv`（`c35a50dd…`）的超集：排除只會整句拿掉，`(月份, 句子)` 在兩邊都唯一。
  2. 凍結的 `clauses.tsv` 每一列，用 `(月份, 句子)` 在超集裡找到同一列，舊前文也要相同；找不到或舊前文不同就停。這樣每一段都拿到新前文。
  3. 照 `period_rows` 用凍結的 `clauses.tsv`、`split.json`（`fd0b1b99…`）與原本的種子重放 tune、chatjudge 的抽樣，套校對檔（`tune.corrections.tsv` `0dcf25af…`、`chatjudge.corrections.tsv` `1f37b583…`；照 `build_period`：整句刪除的列拿掉，改句的列換成新句子），再拿掉句子不在凍結檔裡的列（讀音 CHECK 與讀不出的句子是整句一起丟，所以同一句不會一邊留一邊丟）。剩下的 `(舊前文, 句子)` 序列要和凍結檔逐列相同，不同就停；相同就把每列的前文換成步驟 2 的新前文，句子與讀音照抄凍結檔。
- **discordtune**（`discord-tune-rows.txt` `77e1c90a…`，4,958 列；來源 `discord-tune.txt` `38bbc0f2…`，3,000 則訊息）：
  - 來歷（2026-10-19 用程式核對，只看數字）：列檔是 10-03 用一支沒進 repo 的程式建的。`.in` 5,233 列（`前文|句子`）→ 讀音後 `.all` 5,231 列 → 現行 4,958 列，三者依序是前一個的子序列；研究紀錄寫的「切成 4,982 個子句、拿掉和驗證集重複的 24 個」和這幾個檔的列數對不上（5,231 − 4,958 = 273），中間拿掉的原因沒有留下來，這一片不追，研究紀錄記一筆。用現在的規則重切 3,000 則訊息得到 5,357 段，重現不出 `.in`；4,958 列裡有 989 列的舊前文也不是「同一則訊息的前一串漢字」。
  - 所以接法不重切：每一列的句子都是來源訊息裡完整的一串漢字（4,958／4,958），列也照訊息順序排。把所有訊息的漢字串依序攤平，**每一列從上一列的位置往後找第一個和句子相同的漢字串**，那一串的開頭就是這列的位置，新前文從那則訊息算。核對：(a) 4,958 列都要找得到；(b) 舊前文和句子在來源裡只出現一處的列（2026-10-19 試算 3,946 列），位置必須和這個接法找到的相同。(a)(b) 任一不合就停。試算結果 4,958 列全部找得到，3,946 列全部一致。

**B. HPLT 3.0 繁體的論壇、敘事、評論長文**（GCP `shanjie-work` 上建，Mac 不下載）
- 來源：`https://data.hplt-project.org/three/sorted/cmn_Hant/` 品質最高的兩片 `9_1`（約 0.25 GB）、`8_1`（約 2.1 GB）。下載後算 SHA-256 記錄。
- 篩選：網頁體裁（`web-register`）最高分是 ID（互動討論）、NA（敘事）或 OP（評論）；網址是 `.tw` 網域或 `ptt.cc`、`mobile01.com`、`pixnet.net`（台灣用語，排除港澳）；文件有個資標記（`pii` 非空）就整篇丟掉。
- 段落：文件依換行切段，每段依共同規則切出句子與前文；只留前文 ≥ 16 字的句子（這份集合是量長前文用的）。讀音由 `tools/readings.py` 產生，CHECK 與拼不出的列丟掉。
- 和訓練資料不重疊：把每列「前文最後 16 個漢字＋句子」接成一個字串，用 `experiments/s7a-tinylm/buildcheck.py` 的 `substring_hits`（和 S7a、S7d 同一個函式），只要它是 L0 句子池 `pool.txt`、`wiki.txt`（P2／P3 的訓練列來源，在 `l0train8.tar.zst` 裡，雜湊在 `SHA256SUMS8`）任何一個檔的子字串，就刪掉那一列，報刪了幾列。M 自己的訓練文字 `runs-wiki.txt`、`runs-coll.txt` 在另一台機器上，這一片只用同一個函式另報重疊列數，不刪。
- 抽樣：種子 20261019，最多 3,000 列，每份文件最多 3 列（不讓單一長文主導）。
- 正解是網友打的字，本身可能有選錯的字：main 抽 10%（種子 20261019）校對，記錄改正率；改正率 > 5% 就停，回報維護者。

**C. 維基文庫公有領域散文**
- 來源：維基文庫（zh.wikisource.org）上作者已過世超過 50 年的白話散文（台灣著作權法第 30 條：著作人終身加死亡後 50 年），經 MediaWiki API 以 `variant=zh-tw` 取文字；作品清單另存、記錄每篇的頁面修訂號與 API 回的轉換前後是否相同。
- 段落、句子、前文、讀音、訓練重疊、抽樣規則同 B（前文 ≥ 16 字、最多 3,000 列、每篇最多 3 列、種子 20261019）。
