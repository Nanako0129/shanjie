## 登記（2026-10-19，跑之前 commit）

探索片：只用調參層與開發層，不出貨，結論只寫方向；私人集合只記數字。不碰判讀集、保留集、chatjudge-2。

- **假設**：P2 學生的訓練 KL 從 0.39 降到 0.12，留出卻停在 0.38，比較像資料不夠或不對，而不是模型不夠。蒸餾列裡有 39% 是維基，而 0c 在維基上比 tinylm-v3 差（X0c：wikitune 改對 46、改壞 134），這些列可能在教學生教師的錯。拿掉維基列，學生在聊天上應該更接近 0c。
- **步驟 0：零訓練診斷**（只報、不判）。在同一台 GCP C4D 上：
  - 用出貨設定的 CLI 重新 dump 四個聊天集合（chatclause、discordtune、chatjudge、lytune）。M、P2 學生（`tinylm-S.npz` `06a25d07…`）用 `score.py` 打分，0c 用 `score_0c.py`，放在沒有網路的 namespace 裡跑。
  - (a) 一致率。範圍是 discordtune 與 chatclause 的可改列：n ≥ 2、第一名錯、正解在候選裡、0c 沒跳過。看學生單獨挑的候選和 0c 單獨挑的是否相同，對照 P2 留出集的 79.8%。所有 n ≥ 2 的列也報一次。
  - (b) 字對有沒有學過。範圍是可改列裡 0c 單獨挑對、學生單獨挑錯的列。看兩者所選候選第一個不同的位置上那對字（不分順序），有沒有在 L0 訓練列（`wiki.dump8`、`pool.dump8` 的前 8 個候選）的同一列、同一位置一起出現過，報比例；另報「所有不同位置的字對都出現過」的比例。
  - 沒出現過的居多 → 偏向資料；出現過但學生仍錯的居多 → 偏向容量或目標。這是推論的方向，不是門檻。
- **步驟 1：C-nowiki 臂**。和 P2 唯一的差別是訓練資料：只用句子池（`pool.txt`、`pool.dump8`、`X0C.pool.jsonl`），不放維基。
  - 其他都照 P2：出貨 M 起始、對 0c 的 KL、前文 `context_key`、3 個 epoch、batch 64、學習率 1e-4、warmup 100、留出 2%、種子 20261018。
  - 列數少了，步數會跟著少（約為 P2 的 61%）。這是資料變項的一部分，不另外補步數。
  - 學生檔 `tinylm-C.npz`。
- **打分**：同一台 GCP C4D，C 用 `score.py`；所有臂都在同一種 CPU 上。
- **主讀法**（照 P2）：在 chatclause 調參期用 `select_weighted(cap_ub=0.003)` 選 α／τ／δ。C 在 discordtune 上同時符合以下兩條才算過：
  - 對 M 出貨值（α 0.3、τ 2、δ 0.25）的淨值 ≥ +40；
  - 對 n-gram 第一名的改壞數 95% 上界 ÷ n ≤ 0.5%。
- **只報、不判**：
  - P2 學生、0c、M 同規則的同一張表。
  - C 的前沿表、單獨挑對率與留住率。
  - 留出 KL 與一致率對 P2（0.380、79.8%），訓練／留出 KL 的差（P2 是 0.12／0.38）。
  - chatjudge-2 的 MDE。
- **之後怎麼走**：不論過不過，數字都交給維護者，不開確認片。
  - 診斷 (b) 以沒出現過居多，或 C 明顯比 P2 學生好 → 資料組成有影響，下一步是 HPLT 3.0 繁體的資料片（另外登記）。
  - (b) 以出現過居多，C 也沒變好 → 資料組成不是主因，換容量（L 規模學生）或停。
