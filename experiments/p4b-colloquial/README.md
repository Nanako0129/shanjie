# P4b：口語表在 CLI 全部重打分，照出貨標準對出貨值判讀（2026-10-20 登記）

P4（`experiments/p4-colloquial/README.md`）照登記開這一片：chatclause 選出的格（T2、μ 0.5、γ 0.25）在 discordtune 的 n-gram 層是 +79，但那是對 n-gram 第一名比、最後選字有八成的列要重打分。這一片在 CLI 裡把同一格做完整（重排之後的前 8 名都用小模型打分、照出貨融合選字），直接對**出貨的最後選字**比。這一頁在跑任何 P4b 的數字之前 commit；修訂一（同日，仍在任何數字之前）納入兩位研究顧問（Fable、Argon）的審閱與維護者對第 1 條基準的選擇題。

不出貨、不改核心、不改 App。過了才另開產品片（核心在聊天設定載入表、App、延遲與記憶體、契約）。

## 實作（CLI，評測用，預設關）

- `shanjie-eval` 的 `lm` 模式加三個選項：`--colloquial FILE.sjlm`、`--colloquial-mu X`、`--colloquial-gamma Y`。只在 `--profile chat` 生效（書面時拒絕這三個選項）。沒給 `--colloquial` 時，所有輸出檔與摘要逐位元組和現在相同（測試）。
- 每列：`decode_from` 照舊解出前 64 名（分數 ng、切分 ws；前文照舊只進 ng）→ 每個候選算 s ＝ ng ＋ μ·lc(ws) − γ·k(ws) → 依 s 穩定排序，**分數、切分與字串一起重排** → 前 8 名與它們的 s 交給 `TinyLm::rerank`（ng 換成 s，τ、δ 都看 s）。定義與 `experiments/p4-colloquial/p4.py` 一字不差，容易悄悄不同的地方寫死如下：
  - **口語表**只當純 bigram 讀：不載詞類、KN、三元表（`Lm::load_opts(path, false, false, false)` 或等價），表的目錄裡就算有側檔也不讀。
  - **lc**：起點固定 `<s>`（不接前文）；P(w｜v) 是絕對折扣（D 取表頭），回退到表自己的 (c(w)＋1)／(N＋V＋1)，V 是表的詞彙數（含 `<s>`、`</s>`），表外的詞 c＝0；句尾用表自己的句尾率（剪枝前的句尾總數 ÷ N，同 `BigramLM.eos`）。
  - **k**：從檔案字面建兩個集合：基礎詞庫＝`data/lexicon/mcbpmf-data.txt`；疊加層＝`data/lexicon/overlay-add.tsv` 與啟用的詞包 `data/packs/acg-add.tsv`。**不含** `names-add.tsv`、`sandhi-add.tsv`（和 D3 (ii)、P4 相同）。k ＝ 候選切分裡在疊加層集合、不在基礎詞庫集合的詞數，重複的詞算多次。不用引擎合併後的詞庫（那份分不出來源）。
  - 前 8 名裡有過長候選（`TooLong`）時照舊退回 s 第一名，計數照報。
  - `--dump`、`--dump-words`、`--tinylm-scores` 照 s 的順序寫；這些檔**不能**再餵給 `p4.py`、`d23.py`、`triage.py`（它們把名次 0 當 n-gram 第一名）。
- **對齊檢查**：
  - CI（合成資料）：同一個小表與候選，CLI 的 lc、k、s 和 `p4.py` 的函式相差 < 1e-9；測資要包含一個 `names-add.tsv` 的詞（k 要是 0）、一個重複出現的疊加層詞（算兩次）、表外的詞、句尾回退；μ 0、γ 0 時每列選字和不給選項時相同。
  - **真實資料錨點**（雲端 VM，零新程式）：`--colloquial` 不帶 `--tinylm` 的 rowstats（＝s 第一名）對出貨設定不帶 `--tinylm` 的 rowstats（＝n-gram 第一名），discordtune 要等於 P4 的 168／89、chatclause 179／96；不等就停（抓詞類、KN、k 的集合、浮點末位這些合成表抓不到的差異）。
- 表：P4 建的 T2（`2984eeb5…`），不重建、不改；參數照 P4 選的 μ 0.5、γ 0.25。**不重新選格**。

- **全過** → 開產品片（另寫契約）；但如果**只在新規則下過關**（舊規則會被 dev302 聊天擋下），規則是看過這一格的數字之後才放寬的，開產品片之前要先在沒看過的 chatjudge-2 確認一發（維護者 2026-10-20 選擇題）。**任一條不過** → 這一格不出貨；口語表的變體（修口語計數的「吃→喫」、重新選格）回到探索，再要新的判讀。
- 讀數上的提醒（寫在數字之前）：
  - 第 1 條的 discordtune 是開發層、看過很多次，而且「開 P4b」是看了它在同一批列上的 +79 才開，判讀偏樂觀〔推論〕。所以另報 chatclause（選格用過）與 cvtune-clean 的同一張表並排。
  - 第 2b 條：邊界在任何 P4b 數字之前從 −0.3 放寬到 −1.0（維護者 2026-10-20 選擇題，`docs/methodology.md` 同日一節）：不一致的列約 5% 時 SE 約 0.4 個百分點，−0.3 會擋下約八成的中性改動，−1.0 約兩成〔常態近似〕。出貨的 α／τ 是在 cvtune 上調的，基準在這份集合上有主場優勢；2b 不過時照登記判，紀錄寫明這一點。
  - 第 3 條的錯字集是單邊集（都是選錯過的句子），「+N」照 #2 要配同期隨機抽樣集合的改壞數：配 discordtune 的改壞率一起報。

## 預算、資料、停止條件、範圍外

- **預算**：CLI 實作與 `evalstats` 的分位數選項 1 次＋修正 1 次（工具程式，但改到 `shanjie-eval`：走 `/code-review`＋fresh verifier＋CI）；雲端 VM 打分 ≤ 2 小時（discordtune、chatclause 是私人集合，只在 VM 上，跑完刪；cvtune-clean 與公開集合也在 VM 上，同一種 CPU）。
- **停止條件**：合成或真實資料的對齊檢查不過；不給選項時 VM 上重跑出貨設定的 discordtune 不等於 +107／−26、chatclause 不等於 +111／−26；私人集合的句子或詞被帶回 Mac；要用到判讀集或保留集。碰到就停，回報維護者。
- **範圍外**：核心與 App 的出貨路徑、重建或修正口語計數、重新選格、前文接進口語表、書面設定。
