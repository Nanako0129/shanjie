# P4b：口語表在 CLI 全部重打分，照出貨標準對出貨值判讀（2026-10-20 登記）

P4（`experiments/p4-colloquial/README.md`）照登記開這一片：chatclause 選出的格（T2、μ 0.5、γ 0.25）在 discordtune 的 n-gram 層是 +79，但那是對 n-gram 第一名比、最後選字有八成的列要重打分。這一片在 CLI 裡把同一格做完整（重排之後的前 8 名都用小模型打分、照出貨融合選字），直接對**出貨的最後選字**比。這一頁在跑任何 P4b 的數字之前 commit。

不出貨、不改核心、不改 App。過了才另開產品片（核心在聊天設定載入表、App、延遲與記憶體、契約）。

## 實作（CLI，評測用，預設關）

- `shanjie-eval` 的 `lm` 模式加三個選項：`--colloquial FILE.sjlm`、`--colloquial-mu X`、`--colloquial-gamma Y`。只在 `--profile chat` 生效（書面時拒絕這三個選項，免得誤用）。沒給 `--colloquial` 時，所有輸出檔與摘要逐位元組和現在相同（測試）。
- 每列：`decode_from` 照舊解出前 64 名（分數 ng、切分 ws）→ 每個候選算 s ＝ ng ＋ μ·lc(ws) − γ·k(ws)，定義與 P4 一字不差（lc 用口語表的絕對折扣回退、回退到 (c＋1)／(N＋V＋1)，句尾照 `BigramLM.eos` 用表自己的句尾率，起點 `<s>`、不接前文；k ＝ 只在 `overlay-add.tsv` 或詞包、不在基礎詞庫的詞數）→ 依 s 穩定排序 → 前 8 名與它們的 s 交給 `TinyLm::rerank`（ng 換成 s，τ 也看 s）。`--dump`、`--dump-words`、`--tinylm-scores` 照新的順序寫。
- **對齊檢查**（CI 測試）：同一個小的合成表與合成候選，CLI 算出的 lc、k、s 和 `experiments/p4-colloquial/p4.py` 的函式相差 < 1e-9；μ 0、γ 0 時每列的選字和不給選項時相同。
- 表：P4 建的 T2（`2984eeb5…`，口語計數 `1e7a15ef…`＋公開口語池），不重建、不改；參數照 P4 選的 μ 0.5、γ 0.25。**不重新選格**。

## 判讀（2026-10-20 更正後的出貨標準，`docs/methodology.md` 同日一節；全部對現行出貨值比）

## 預算、資料、停止條件、範圍外

- **預算**：CLI 實作 1 次＋修正 1 次（走 `/code-review`＋fresh verifier＋CI：這是工具程式，但改到 `shanjie-eval`）；雲端 VM 打分 ≤ 2 小時（discordtune、chatclause 是私人集合，只在 VM 上，跑完刪；cvtune-clean 與公開集合也在 VM 上跑，同一種 CPU）。
- **對齊**：P4 在 VM 上的 T2 檔與 CLI 讀的那份核對雜湊；不給選項時，VM 上重跑出貨設定的 discordtune 要等於 P3／D1 的 +107／−26，chatclause 等於 +111／−26，不等就停。
- **停止條件**：對齊檢查不過；私人集合的句子或詞被帶回 Mac；要用到判讀集或保留集。碰到就停，回報維護者。
- **範圍外**：核心與 App 的出貨路徑、重建或修正口語計數、重新選格、前文接進口語表、書面設定。
