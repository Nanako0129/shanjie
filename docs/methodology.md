# 善解的評測與迭代方法論

這份文件記錄善解怎麼衡量「選字選得對不對」，以及怎麼決定一個改動要不要留下。依時間的實際過程、每一輪的數字與犯過的錯，記在 `docs/research-log.md`。這兩份文件會持續更新，之後整理成公開文件。

## 1. 問題與指標

注音輸入時，使用者打的是讀音，輸入法要從同音的字詞裡選出想要的那一串。

- **整句正確率（top-1）**：輸入法第一個給出的整句和正解完全相同的比例。以子句為單位，寬鬆對照把「她妳它牠嘗周臺裏」視為「他你他他嚐週台裡」，再把教育部《重編國語辭典修訂本》明列「也作／亦作」、讀音相同的異體詞視為相同（`eval/variants.tsv`，2,072 個異體；**事後修改**：2026-10-03 看過 dev302 錯句後由使用者決定，標準定死在辭典本身，不從評測句挑；之前的數字是舊規則）。
- **候選上限（oracle@K）**：正解出現在前 K 名候選裡的比例，判斷器只能從候選裡挑，所以這是上限。目前 K = 64。
- **對數損失**：前 64 名候選的分數取 softmax 後，正解機率的負對數；正解不在候選裡記為上限 10。它比對錯計數更連續，適合調參數。
- **延遲與大小**：每打一個音節重新產生候選的 p95（要求 < 16 ms）、詞庫與模型的記憶體。

錯誤分兩種，對應不同的修法：

- 正解根本不在候選裡：詞庫或搜尋的問題（S1、L）。
- 在候選裡但排錯：語言模型或判斷器的問題（S2、S5、S6）。

調整集必須**不參與任何計數**：用固定的雜湊切分，或取計數範圍以外的資料。

**挑戰集的結果不能當結論（2026-10-05）。** S5j 的 Apple 判斷器在 dev302 上 +27 列、p = 0.0003，在使用者的 discordtune 上卻是 −81 列。dev302 的句子多半是專案或 LLM 寫的，和真實聊天的分布不同。任何改動在挑戰集上的好結果，只能當作「值得在調整集上量」的線索。

**探針集（S2r 起）。** 評測集的讀音是一個人一種打法，量不到「同一句用另一種合規讀音打」的情況。探針集從現有集合取含「一」「不」的列，依詞庫生成器同一套規則（`tools/build_sandhi.py` 的 `yi_keeps_base`）把每個可換的位置換成另一種教育部合規讀音（本調↔變調），一列產生一個探針列；沒有可換位置的列略過。產生器是 `experiments/s2/build_probe.py`（`--check` 重產比對）。公開的 dev302＋typing76 探針放 `eval/probe/s2r-probe.txt`，不放 `eval/dev/`，以免改變「開發集前 302 列」；cvtune 探針因為含 Tatoeba 句子只放本機；discordtune 探針放私有目錄。探針集沿用原集合的角色：cvtune 與 discordtune 的探針是 gate，公開探針只記錄。比較時和同一批列原本的讀音配對：先確認現況下換讀音確實變差（前提），再比較改動前後的探針結果，並另外用原讀音確認不退步（`experiments/s2/s2r_eval.py`）。

## 3. 一次迭代

1. 改動前先寫下預期會動到哪一類錯誤。
2. 用 `experiments/s2/iter2.py` 跑一個或多個設定。每句都記下對錯、正解名次、分數差和對數損失。
3. 用 `experiments/s2/compare.py` 和基準逐句配對比較：修好幾句、弄壞幾句、McNemar 精確檢定、bootstrap 95% 區間。
4. **採用規則**：
   - 在大調整集上，配對檢定要顯著（p < 0.05），淨效果為正。
   - 驗證集只做「不劣性」檢查：退步不超過一個配對標準誤就算過。
   - 挑戰集的變化只記錄，不當否決條件。
5. 結果記進 `experiments/s2/log2.tsv`，決定與理由記進 `docs/research-log.md`。

**逐列統計與報法（2026-10-08，使用者決定，從下一片開始）。** 只報總數看不出是「改對 1 句」還是「改對 3 句、改壞 2 句」，227 句上差 1 句也遠在雜訊內（配對精確符號檢定要改對對改壞差到約 6 比 0 或 9 比 1，p 才小於 0.05）。所以每個集合（保留集、dev302、typing76、錯字回報、Discord 調參集）在聊天與書面各報一行：n、top1 基準／新、改對／改壞、精確 McNemar p（Dietterich 1998）、CER（各列字元錯誤數總和 ÷ 正解字數總和）基準／新、Δtop1 與 ΔCER 的配對 bootstrap 95% 區間（Koehn 2004；同一批抽樣）。資料是 `--rowstats` 寫的逐列檔（每列 `列號\t對錯\t錯字數\t正解字數`，只有數字、不含文字，所以保留集也能寫），比較用 `tools/evalstats.py compare`；調參時 cvtune、wikitune 的前後比較也用同一張表。對錯沿用既有的寬鬆 top-1，同一個判斷不重算；寬鬆算對的列錯字數記 0。CER 是以第一名 surface 對正解句的 Levenshtein 距離（Unicode 純量值）算的，是補充指標，不取代整句正確率。這次 S2k 的結果不重跑。`tools/bench.py` 的跨版本表尚未改（見 `docs/PLAN.md`）。

**解析度。** 一句對一句錯的雜訊不能當成進步。依 Fable 5.1 的估算，在改動影響約 4% 句子的假設下，配對比較要達到 5% 顯著，淨增益要大約：dev302 2.3 個百分點、typing76 4.5、Discord 845 1.4、新聞 294 2.3，一萬兩千列約 0.35。

## 4. 防止過度擬合的規則

- 不准從評測句挑詞加進詞庫；新詞只能來自可再散布、獨立於評測的來源，並能從鎖定版本的來源完整重建（`tools/build_overlay.py --check`）。
- 合成語料的提示詞只寫主題、語氣或混淆字類別，不放任何評測句。
- 看過驗證集或保留集之後才修改的門檻或規則，要在文件裡標明「事後修改」。
- 已參與選模的集合，不能再當獨立的驗證。

**污染測試怎麼定義退步。**（2026-10-05，S4 全域加分）用「輸出和沒學習時不同」算退步，會把原本就錯、變對的列也算進去（近世→近視），結果在最小的 ε 上也看到退步；改成「這一列原本整句等於期望、之後不再等於」才是退步，且文件、程式、發佈的表三處要用同一個定義。第一版程式用的是「句子含期望的詞」，文件寫整句相等，表上的數字是用前者量的，直到審查才發現。另外要寫清楚三件事：哪些列算污染列（期望是「沒被教的詞」的列，不一定是 kind=common）、碰撞怎麼判斷（解碼用的前文 key 取決於 beam 裡的假設，從外面只能近似，要說明近似了什麼）、讀不出 key 的列另計，不要悄悄當成碰撞或悄悄排除。

## 5. 外部輸入法的比較

`tools/imetype.swift` 用相同的注音按鍵，把句子打進三套現有輸入法：macOS 內建注音、小麥注音、自然輸入法。每句打完按 Return 送出，不選字。注意事項：

- macOS 內建注音會學習使用者平常的打字，也會在測驗過程中學到測驗句。以後要做公平比較，測驗前先備份它的學習檔、測完還原，或在測驗期間關閉學習。
- 自動打字的讀音來自 `tools/readings.py`；破音字無法自動判定的句子不打。讀音標錯會讓每一套一起錯，例如「欸」曾被標成 ㄞˇ。

## 7. 殼層讀 client 的行為要在實機確認

殼層測試用的假 client 照 NSTextInputClient 文件實作，量不到真實 App 的回報方式。2026-10-06 的實機日誌顯示，多數 App 在沒有 marked text 時回 `{插入點, 0}` 而不是文件寫的 `{NSNotFound, 0}`，前文因此從 S4 合併起在這些 App 都讀不到，測試全綠也看不出來。

- 讀 client 狀態（插入點、marked text、前文、行矩形）的程式，合併前在幾個常用 App 實機打一次，用**只記數字**的暫時日誌確認讀到的值，日誌不 commit。
- 實機看到的回報方式補成假 client 的測試案例，讓之後的改動回不去。

## 先確認使用者改字的原因，再設計行為（2026-10-08）

改選固定修了四輪，每輪 review 都在同一份「放開紀錄」上找到新的邊角，最後一輪還讓常見的打字流程變差。回頭看，起點的回報（「版控」改「版」後「控」變「空」）有兩個成分：缺詞（「版控」不在詞庫，量過）與改選後的重算；使用者指出前者可能才是根本（推論，還沒量回報裡有多少屬於缺詞）。使用者改字，可能是因為詞庫沒有他要的詞。設計「改字之後怎麼辦」之前，先量回報的錯字裡有多少是缺詞、多少是排序錯，選字行為的改動要用「改選後繼續打字」這類真實流程的模擬當關卡，而不是只用單一例子。

## 改到已經決定過的地方，先讀研究紀錄裡同主題的條目（2026-10-08）

安裝流程第二版的第一份契約（`docs/contracts/installer-v2.md` 的第一版）寫了「brew 的 postflight 自動註冊」，plan-verifier 指出這條路 2026-10-04 就判斷過走不通，研究紀錄也寫了。那次是讀 Homebrew 原始碼得到的結論：postflight 在沙盒裡跑，讀不到家目錄，`~` 也不展開。當時沒有實測，TIS 在沙盒裡能不能註冊也沒量過。契約是照當下的想法寫的，沒有回頭查。

- 契約要改的東西如果以前有過決定（s3b、s3c 的某一節、研究紀錄某一天），寫之前先搜研究紀錄和那份契約的同主題段落，把舊結論和它的證據列進新契約，再說明這次哪裡不同。
- 舊的未驗證項目（例如「`on_upgrade` 要到第二次發版才測得到」）到了能測的時候，先去找實際的結果（這次是 Discord 上使用者的回報），再決定要不要改設計。

## 「沒發生」幾次不能推翻使用者反覆的觀察（2026-10-09）

2026-10-05 看到「同一天裝了多次新版，Caps Lock 都正常」，就寫下「安裝會觸發不成立」。使用者後來說「每次更新完都會故障」，2026-10-09 逐項控制變因（同一份 0.3.0，每次只改一件事，每步由使用者按 Caps Lock 回報）才證實使用者是對的：觸發條件是「bundle 換過之後再註冊或啟用」，而當天那幾次安裝剛好沒有同時具備。

- 使用者反覆回報的現象，不要因為自己試了幾次沒重現就否定；先找出自己的幾次少了哪個條件。
- 要判斷某個動作和使用者看到的現象有沒有關聯，用單一變因的對照：一次只改一件事，每步都讓使用者回報結果，而不是看「裝了幾次都正常」。

## 重建模型時，一般詞要和上一版逐列相同（2026-10-10，model-v5）

model-v5 讓詞包詞進斷詞詞彙。為了守住一般打字，前後修了四次，每次都是量到了才知道：

- **吸收**：詞包的兩字片段把常用字對的計數吃掉（萊＋恩 1,336 → 0），不開詞包的評測就變差。改成加法計數，一般詞的計數照不含詞包的切法。
- **片段**：只排除整個有衝突的詞不夠，片段（艾莉、伊莉）有計數，拼起來還是同一個名字。排除要看讀音：衝突讀音裡連續兩個以上音節的詞包詞都不計。
- **詞類漂移**：計數完全相同的一般詞，重新分群後類別整體漂移，探針書面 69 → 66 句。`--no-classes` 時兩個模型相同，才確定原因在分群。改成舊詞沿用上一版的類別，只替新詞找類別。
- **扣分的對象**：調扣分前先確認要救的詞真的「沒見過」。越角、擦聲、黴變其實都有計數，扣分作用不到它們，只會壓低沒見過的詞包名字。

教訓：
- 改模型時先定一個「不該變的部分」（這次是不開詞包的一般集合），量到它逐列相同才往下走；差一點也要找出原因，不要用「不顯著」帶過。
- 用 `--no-classes` 這類開關把模型拆開比，最快找到差異出在哪一層。
- 從文字檔取注音讀音、去重複時用位元組排序（`LC_ALL=C sort -u`）；中文語系的 `sort -u` 會把不同的讀音當成相同（78 個只剩 19 個）。`awk` 比字串也一樣，加 `LC_ALL=C`。
- 停止條件的每一類都要報：第一次衝突重驗只報了 78 個讀音，漏了約 190 個 (c)。

## 2026-10-10：CLI 評測前核對模型、收尾步驟別拖到發版後、句數與列數分開報

- **跑 CLI 評測前先核對模型雜湊**：`shasum -a 256 -c data/bigram.sjlm.sha256`。本機的 `data/lm/bigram.sjlm` 還是 model-v4（model-v5 合併時沒有換檔），用它量名字回報得到錯的結論，事後撤回（研究紀錄 2026-10-10「v0.4.0 發佈後的名字回報與量測」）。
- **契約的收尾步驟（保留集）要在 Release 之前跑完**：model-v5 的保留集漏跑，發佈後才補量；結果雖然沒變，但發版前審查寫的「含保留集」並不成立（契約 `docs/contracts/model-v5.md` 的〔更正〕）。
- **同一個集合在兩種設定各量一次時，句數與列數分開報**：cvtune 加 wikitune 約 6,600 句，聊天與書面各量一次是約 1.3 萬列；「4 處變差」是四格（兩個集合、兩種設定）裡的列次，不是 4 句。

## 2026-10-10：把一個階段抽出來共用時，後面的過濾也要一起帶走

- KN 側檔（`tools/kn_cont.py`）共用 `build_lm` 的計數階段（`merged_counts`），但 `build` 在那之後還會丟掉前文不在詞彙裡的詞對；側檔沒有照丟，接續次數多數了模型不收的前文（研究紀錄 2026-10-10 KN 那一節的更正）。量到的影響很小（θ=1 一個詞的 N 少 1），但產物的雜湊變了，之前用舊產物量的保留集與探針都要標明。
- 做法：共用一個階段時，把使用端在那之後做的過濾也列出來，測試要比對「使用端實際保留的東西」，不是只比共用階段的輸出；產物改了就逐項標明哪些數字是用舊產物量的。

## 2026-10-11：相加的分數要同一個對數底；分類器的類別比例就是先驗

- P1a 把分類器的 `f`（自然對數）加到 n-gram 分數（log10），契約沒寫底，格點的 μ 因此大了 2.3 倍（研究紀錄 2026-10-11 P1a 那一節的更正）。契約寫融合公式時，要寫明每一項的對數底；測試用手算值時也用同一個底。
- 分類器每類取樣有上限時，輸出的 `P(c｜x)` 帶的是訓練樣本的類別比例。要和已經含先驗的分數（n-gram）相加，先決定要的是後驗還是似然項，再照樣本比例修正；不要只用一個整體的權重去「補」。
- 比較兩個方法時，兩欄的條件要相同：分類器用正解句的前後字、n-gram 用解碼結果，兩者不能直接比。

## 2026-10-12：過濾條件先在來源上量命中數；比較模型時也在同一組值上比（S7f）

- **過濾條件要量命中數**：S7f 照契約字面用 `Wikipedia:互助客棧` 選互助客棧，但中文維基的頁名是簡體的 `Wikipedia:互助客栈`，manifest 裡 namespace 4 只有 2 頁，A1 訓完才發現、整組重訓（研究紀錄 2026-10-12 S7f）。用標題、命名空間、標籤選資料時，先用來源自己的查詢（API、dump 的標題清單）量一次「應該有幾頁」，和清理後 manifest 的頁數對照，差太多就停。中文站的標題可能是任一種寫法，兩種都要查。
- **清理的殘留要看輸出才找得到**：維基討論頁的簽名格式有好幾代，第一版的規則只認得最新的格式；每次清理完都抽樣看輸出、數殘留樣式的比例，再決定要不要重跑。
- **選值與判斷不在同一個語域時，另外在同一組值上比**：S7f 的四組各自在公開調參集（書面為主）上選值，判斷用使用者的聊天；加了真人口語的模型選到改動更多的值，判斷沒過。但在比過的四組共同值下，它在聊天的改壞不多於基準（重做資料後的 A1；重做前的 A1 在其中一組值多 1 列，加了生成句的 A2 也不一定）。只看「各自選值後」的結果，會把「選法不能轉移」誤當成「資料沒有幫助」。之後比較訓練資料時，除了照契約的選法，也在幾組共同的值上列表（只當參考，不拿來挑值）。
- **丟句規則要看「因為哪個字被丟」**：S7f 第一次用了 `build_counts.SIMP_ONLY` 判斷簡體句，它含「群、床、秘」等 14 個台灣常用字，含「社群、起床、秘密」的句子全被丟掉（Cofacts 簡體拿掉 79,779 句，修正後 47,333），本地 /code-review 才找到，資料整批重做。每條丟句規則除了總數，也印出觸發最多次的字或樣式，前幾名一眼就看得出來是不是誤殺。專案裡名字相近的字集（`SIMP_ONLY`、`TRAD_SIMP_ONLY`）先讀它的註解，確認是給同一種輸入用的。
- **一次訓練、一次選值的淨值很不穩**：S7f 重做資料之後，同一組的淨值（改對 − 10 × 改壞）在兩次之間差 80 和 64，比只換平台與種子的 A0、A0′ 之間的 32 還大，原因還不一樣：A2 兩次選到同一組值，模型本身就變了（改壞 28 → 22）；A1 兩次選到不同的值，比過的共同值下兩個模型接近，推論差別主要來自選值（兩個 A1 沒有在彼此選到的值上打過分）。這種淨值只能當粗略的方向；要比較訓練資料，同時看同一組值的表，並多訓幾個種子。
- **雲端 API 的推理參數要先量**：Gemma 4 送 `reasoning: low` 時每次多出約 600 個推理 token，每次 US$0.00027（不送參數時推理 token 是 0、每次約 US$0.00002，約 13 倍）；時間上，16 個並行呼叫一批約 44 秒，不送參數時單次約 1.4 秒（兩個數字的量法不同，沒有量同樣條件下的單次延遲）。生成前先用幾十次呼叫量 token 數與費用，再決定參數。

## 2026-10-12：權重先算天花板再定（評測與計分）

「改壞 1 句 ≈ 改對 10 句」是看過嚴格點之後才選的（S7e 契約開頭）。這個權重下，就算直接在判斷集上挑值，最好的淨值也只有 +17～+23／4,091 列（A0 +17、A0′ +19、A1 +17、A2 +23），和 S7f 的雜訊界線（A0 與 A0′ 差 32）同一量級，任何改動都量不出來；同時把 1:1 下已經量到的進步（S7a 的 +67、S7f 口語文字的改善）全部算成失敗。教訓：定一個權重之前，先在已有的分數上算出它的天花板與雜訊；天花板比雜訊小，就改用另一種寫法表達同一個偏好（例如 1:1 計分加改壞率上限）。另外，選值用的集合語域不對時，換權重也救不回來：選值與判斷要用同一種語域的資料。

## 2026-10-13：評測集不拿來訓練；當線索時，當過線索的列不評分

維護者問「能不能把錯字的答案直接訓練」。`eval/dev/user-reported.txt` 是唯一量真實使用者錯字的集合，拿來訓練之後就量不出沒看過的句子有沒有變好。決定（選擇題）：錯字檔只當評測，錯字裡的詞可以當補語料的線索。但用某些列挑了語料，那些列再拿來評分就會偏高（挑資料的集合等於評分的集合）：評分只用沒當過線索的列，例如那一片開始之後才回報的列，或事先固定留一半不看；dev302 裡的列不當線索。

## 2026-10-13：比詞的強弱要看組字時用的分數，不是詞庫檔的分數

## 2026-10-13：拿掉一項資訊的對照，要用模型看過的輸入

X0c 想知道 0c 贏在聲調還是前文，做了兩種「拿掉」：把每個音節都當一聲（`llr`）、把前文清空（`ll0`）。/code-review 指出兩者不可比：全一聲是模型沒看過的錯誤輸入，選擇變了可能只是輸入壞了，不代表聲調有用；清空前文連對手也看得到的部分都拿掉；「前文較長」的比法幾乎一定成立。結論只能寫「兩種拿掉都會改變選擇」。要比兩個因素，每個對照只改一件事，而且用模型訓練時見過的形式（例如把前文截到對手的長度），比之前先問「這個對照改變的是不是只有我想量的那一項」。

## 2026-10-18：研究流程改版（探索與確認、改壞率上界、最小可偵測效果）

三位審閱者各自檢視之後，維護者 2026-10-18 用選擇題採用下列規則；計畫與理由在 `docs/iteration-plan.md`，經過在研究紀錄同日一節。

1. **兩軌。** 探索：一頁登記（假設、指標、集合、預算、停止條件），只用調參層與開發層集合，不出貨、不碰判讀集與保留集，結論只寫方向。確認：一頁鎖定並先 commit（一個主判讀、判讀規則、集合、預算、最小可偵測效果與診斷），在沒看過的判讀集上一發；不過就結案，不開子片救援；變體回到探索，再確認要用新的判讀集。看過結果後改門檻、篩選、集合或格點，那次確認就作廢。「契約不要訂得過嚴」只適用產品與 UX 規則，不適用統計判讀規則。
2. **集合分層。** 回歸層：dev302（2026-10-20 起只擋書面設定，聊天設定只報，見本檔同日一節）、打字測驗、probe、wikitypo、錯字回報（要求逐列相同，或改壞 ≤ 2 且淨值 ≥ 0；表格照舊印 p，但不用 p 判；錯字回報是只在出錯時收的單邊集，只看改壞方向，「+N」一律配同期隨機抽樣集合的改壞數）。調參層：chatclause 調參期、cvtune-clean、wikitune-clean。開發層（看過）：discordtune、lytune、fw、退役的判讀集。判讀層：chatjudge-k、wikijudge-k，一份只用在一個決定，用過就退役；2026-10 以後用善解打的文字不當選值或判讀的正解。災難偵測：現役保留集，只在推 `v*` tag 前由 fresh verifier 跑一次。選值與篩選只用調參層；非劣性守門用開發層（例外：2026-10-20 起聊天出貨標準用 cvtune-clean 守門，見本檔最後一節）；主判讀只用判讀層。
3. **判讀集的形狀。** 凍結時切成三個固定子集：J-對（n-gram 第一名就對）、J-錯在前 8、J-錯在 8 外（AJIMEE-Bench 的做法：可接受多個答案、有無前文分開報）。子集用來分解：改壞只會出在 J-對、改對只會出在 J-錯在前 8，各自報列數；改壞率的門檻仍以整集 n 為分母（#4）；整集的精確 McNemar 仍是主判讀。
4. **改壞率用上界。** 0.5% 上限與分母不變（R3′：改壞 ÷ n），只把點估計換成上界：選值與判讀都用改壞數的 95% 單尾精確 Poisson 上界（`evalstats compare --net` 印的那一欄）÷ n 和上限比。這比點估計嚴，例如 n 3,000、改壞 7 列：點估計 0.23%，上界 13.15 ÷ 3,000＝0.44%。「改壞」是最後送出的錯；另報「顯示後被改掉」、error ratio（新造的錯 ÷ 修好的舊錯）、每千字改壞數。確認片的格點事先固定、不超過 24 格（探索片不限），表上印「改對 vs 改壞率」前沿。起因：用選值集上的點估計時，選到的值都壓在上限邊緣，到新資料就超過（rerank-formal 0.50% → 1.72%；rerank-size XL 0.43% → 0.54%）。
5. **一個主判讀，守門用非劣性。** Holm 的家族＝餵進同一個決定的檢定。使用者端集合的守門：n ≥ 1,000 時 Δtop1 的 90% 配對 bootstrap 區間下界 ≥ −0.3 個百分點；n < 1,000 時淨值 ≥ 0 且改壞 ≤ 2。不再用「任一格 p < 0.05 且淨值為負就否決」（十幾格各自檢定，零效果下也常有一格誤否決）。
6. **叢集 bootstrap。** 同一則訊息、同一段發言、同一個條目切出的列彼此相關，bootstrap 以叢集重抽。
7. **每版 KPI 與停損。** 每個發版填一列聊天與書面的 KPI（`docs/iteration-plan.md` §6）與錯誤桶表；連續三個確認片 KPI 不動，就停下來換方向。
8. **預算。** 探索片寫 Colab 單元、Windows 機器小時、校對小時；超過 1.5 倍就停下來問；確認片超過就結案。
9. **最小可偵測效果與診斷先行。** 開確認片前，先用既有分數檔印診斷（小模型單獨挑對率、留住率、融合上限、oracle），並用基準在同類判讀集的不一致列數、主判讀的 α 與 n 算 80% 檢定力的最小淨值〔精確二項：不一致 61 列時，α 0.05 是 +23 列，Holm 第一關 α 0.01 是 +27 列；淨值和不一致列數同奇偶，不考慮奇偶的連續值是 +22.1、+25.9〕；診斷的估值低於它就不開確認，改做探索或加大判讀集。rerank-size 事前就能算出它幾乎不可能判出 +10 列級的效果。
10. **多種子。** 比較模型時每臂至少 3 個種子，調參期挑一個、判讀一次，報全距；只換平台與種子，淨值就可能差幾十列。
11. **讀音。** 評測讀音的產生規則改動前，先在 200 列抽樣上報錯誤率（< 5% 才用），每個集合報受影響列數與「CHECK 或讀不出而丟掉」的比例；有真實按鍵集之後以它為準。
12. **似然不蓋詞圖。** 重排器只在校準後的信心超過門檻時才改 n-gram 的第一名，不以「分數比較高」為理由直接覆寫（文獻與自家數字都指向同一件事：librime-witogram 把搭配表換成似然後 top-1 下降；出貨的小模型單獨挑時會改掉 8–13% 原本對的第一名）。

## 2026-10-18：同一次比較的各臂，在同一種 CPU 上打分

同一份 135 列在 Windows 機器與 GCP（AMD EPYC 9B14）各跑一次：選字、n-gram 分數、`top1_sha256` 相同，小模型分數每列都差，最大 7.1×10⁻⁶。用分數選門檻或比淨值的比較（例如 S7f 三種子對 M 出貨值），所有臂要在同一種 CPU 上打分；換機器時整批重打，不和舊分數混用。只比選字結果的表（錯誤桶、top1）跨機器可比，但仍以 `top1_sha256` 逐格核對。

## 2026-10-19：更新流程要從舊版的配置開始測，中間不重開機

沙盒版經 Sparkle 更新的失敗，在虛擬機（macOS 26.6.2）上是「同一條路徑開機後先跑過沒有 XPC 服務的舊配置」時出現，重開機就消失（研究紀錄同日；黑箱量測，機制是推論，其他觸發條件沒量）。全新安裝、或每一步之間重開機的測試都看不到它。所以更新流程的驗收從使用者手上真正的舊版配置開始，依序換版，中間不重開機；實機的更新也記下開機時間，才知道量到的是哪一種情況。

- 〔2026-10-20〕這個「XPC 服務照路徑被系統記住」的問題，最後是用「不放 XPC 服務」解掉的：安裝改由 bundle 裡不在沙盒的「善解更新」在自己的程序裡做，輸入法 bundle 裡沒有任何 `.xpc`，系統就沒有東西可以照路徑記（`docs/contracts/standalone-updater.md`）。比修訂三的「換資料夾、服務組合一變就再換」乾淨：那條規則要每次換版都記得，而且只是繞過一個機制沒弄清楚的快取。教訓：碰到系統照路徑快取的黑箱行為，先問能不能讓那個東西不存在，再考慮躲開它。

## 2026-10-19：改模型的輸入長度，評測集的輸入也要那麼長

P3 把學生的前文從 2 字加長到最多 63 字，評測集的前文欄卻只有一串很短的漢字（研究紀錄同日）。在這種集合上量，「長前文有沒有用」量到的只是短前文的情況，加長訓練反而可能被懲罰（訓練時看到長前文、評測時看不到）。改模型的輸入範圍（前文長度、讀音、跨訊息）之前，先確認評測集的對應欄位真的有那麼長，必要時先重建評測集；否則結論只能寫「在短前文下」。同一片也確認了：基準要用出貨檔本身（int8 還原的權重與檔頭的值），不是訓練時的 f32 檔與手寫的值。

## 2026-10-20：網路文字當評測集，SEO 插詞濾不乾淨

- HPLT 3.0 繁體的論壇、部落格長文，三次各抽 300 列校對都超過 5%（12.7%、5.3%、6.7%），主要不是錯字，是 SEO 工具把**真的詞**插進句子中間、內容農場與改寫器的產物。插入詞是正常詞，n-gram 的每字分數、重複子字串這類便宜的訊號都分不出來，每加一道規則只是追著樣本跑。
- 教訓：網路文字當評測的正解之前，先抽小樣本看垃圾的**形態**；如果是「真詞插入」這一類，不要指望關鍵字或分數門檻，直接換來源（有編輯過的文字），或改用模型判斷（要另算成本）。研究紀錄 2026-10-20。
- 「有編輯過」也不保證乾淨：維基文庫的公有領域散文，37% 的作品是簡體原文、`variant=zh-tw` 沒轉；濾掉之後剩下的作品裡，學術著作的文言引文又佔了一大塊（第二次校對整體要改 13.8%，其中整列丟的 30 列多半是文言引文）。公開長文當正解前，先看來源的組成（文字系統、文體），再決定要不要用，不要指望事後過濾。

**2026-10-20：以 root 處理使用者給的檔案，先驗證、再做任何會跟連結的動作。** U2 的 root 階段第一版在驗簽章之前就對副本跑 `chmod -RN`，而 `-N` 會跟符號連結走（`chown -R`、`chmod -R <權限>` 不會），變成可以被同使用者借去改 bundle 外檔案的混淆代理。教訓：以 root 處理使用者寫得到的來源時，複製進 root 擁有的目錄之後，第一件事是驗證（`codesign --strict` 會拒絕指向外部的連結），驗過之後的動作也一律不跟連結；工具的「遞迴」選項是否跟連結要逐一量，不能假設一樣。同一片也量到兩件會把權限或 ACL 悄悄帶過去的事：`umask 077` 下 `tar -xf` 會把 bundle 變成 0700／0600（要 `tar -xpf`，而且 `stapler` 在同一個 umask 下寫出的檔也是 0600，所以權限要在蓋章之後修）；`ditto --noacl` 在 macOS 27 上沒有拿掉 ACL。
