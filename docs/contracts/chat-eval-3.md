# CE3：重建聊天評測集（評測片）

狀態：草稿（2026-10-27），plan-verifier 兩次 REVISE 都已逐項修正（第一次：判讀集時間窗、頻道 id、「不讀」的定義、預算回滾；第二次：和舊集過渡決定矛盾的句子、訊息 id），待收尾審查。

## 0. 起因與維護者的決定（2026-10-27）

- 舊的聊天集合（`chatclause`、`discordtune`、`chatjudge-1`、`chatjudge-2`，以及 SJ-LM-7 留給 `chatjudge-3` 的保留桶）收了維護者在多個 Discord 伺服器、以及沒有伺服器名稱的頻道裡的訊息。維護者決定：**Discord 只用維護者指定的一個伺服器的公開頻道**，其他伺服器與不明伺服器都不用；Facebook、Threads 自己的貼文與留言照舊可用。
- 舊集合的過渡（維護者同日）：到會意 L 為止（含 SJ-LM-7 的判讀、N、W、L 對 R1）舊集合仍可用，先拿掉稱呼與故意錯字的列、核對正解，分數在過濾後的集合上重打（這件事不在這一片）。L 之後只用這一片的新集合，舊數字不跨集比較。
- 維護者的其他決定（同日選擇題）：
  1. 正解含暱稱、稱呼或故意的錯字（例如把色色打成「瑟瑟」）的列，從聊天集拿掉。
  2. 新來源：維護者自己的 Threads、Facebook 與那個伺服器；兩個公開微網誌平台的小抽樣（下稱 M1、M2；官方 API、沒有明確授權：私下用、不具名、只發統計；名稱只在維護者本機的筆記）；PTT（「訓練和評測可以都用，重複也沒關係，因為訓練不一定 100% fit」：評測列不必避開 SJ-LM-7 的訓練文字）。
  3. 舊集合到會意 L 為止仍可用（見下一點）；模型與 Moore–Lewis 已挑的語料不動。
- 這一片**只建集合**，不改核心、不訓練、不改出貨值。出貨標準第 1 條的改法維護者已決定（§6）。

## 1. 要做到什麼、怎麼看到

- 三層新集合取代舊的四份：
  | 新集合 | 層 | 取代 | 用途 |
  |---|---|---|---|
  | `ctune` | 調參層 | `chatclause` 調參期 | 選值、篩選 |
  | `cdev` | 開發層 | `discordtune` | 出貨標準第 1 條、每版 KPI、非劣性 |
  | `cjudge-k`（k = 1, 2, …） | 判讀層 | `chatjudge-k` | 確認片一發，用過退役 |
  | `cmicro` | 開發層（只報） | 無 | M1、M2 的小抽樣，只報、不擋 |
- **怎麼看到**：研究紀錄一節，每份集合一列：每個來源的訊息數、列數、各條排除的列數、校對抽樣的錯誤率、讀音 CHECK 丟掉的列數、SHA-256。另一張表：現行出貨（v0.5.0 的設定）對 n-gram 第一名在 `ctune`、`cdev` 的聊天 top1 與改對／改壞（新的基準線）。
- 之後：會意 L 之後的片，出貨標準第 1 條在 `cdev` 量、選值在 `ctune`、確認一發用 `cjudge-1`（SJ-LM-7 與 L 用過濾後的舊集合，見 §0）。這些各自在自己的片裡做，不在這一片。

## 2. 來源與讀取範圍

- **時間窗**：所有來源只取 2015-07～2026-08 的文字；**判讀集（`cjudge` 池）只收 2015-07～2026-07**（維護者的判讀集規則），落在 `cjudge` 桶的 2026-08 訊息不進任何集合、只計數。M1、M2、PTT 是別人的文字，2026-09 那條不適用，但用同一個時間窗。
- **「不讀」的定義**（維護者自己的 2026-09 訊息，以及窗外的訊息）：匯出檔一個檔含所有月份，所以「不讀」指：時間戳一解析出來，窗外的訊息（2015-07 以前、2026-09、2026-10 以後；時間戳讀不出來的也算）**當場丟掉**，在任何看文字的函式（網址、個資、程式碼、斷句、去重）之前；只留每月的則數。它們的文字不會出現在 `clauses.tsv`、`counts.json` 或之後的任何檔案。

### 2.1 S1：維護者自己的文字（私人）

- 讀取範圍照 `docs/contracts/e2-chat-eval.md` §2.1（Meta 匯出的四個確切路徑、Discord 只讀訊息資料夾、私訊排除、個資與密鑰過濾、網址與程式碼排除），**另加伺服器篩選**：
  - `build_chatclause.py` 加 `--guild ID`（給 `--discord` 時必填）：每個頻道先讀 `channel.json`，`guild.id` 不等於 ID、或沒有 `guild` 的頻道整個跳過，不開它的訊息檔；照原本的頻道類型篩選之後再套這一條。各原因跳過幾個頻道會印出來。
  - 伺服器 id 由維護者在命令列給，不進 repo。
  - 找不到任何 `guild.id` 等於 ID 的頻道：停。
  - 單元測試：合成的資料包裡放兩個伺服器與一個沒有 `guild` 的頻道，只有指定伺服器的訊息出現；另外兩個頻道的訊息檔不被打開（用不存在的檔名或讀取計數斷言）。
- 列的單位、前文、排除照 e2 §2.1（子句 2–30 字；同一則訊息的前一段、或同頻道 10 分鐘內本人上一則的最後一段）。

### 2.2 S2：PTT（公開）

- 來源：SJ-LM-7 用的 2026-10-25 快照（`<board>/<article>.html`，雜湊照 SJ-LM-7 契約記錄的那一份），只用**推文**（`ptt_clean.merged_pushes`：同一帳號 3 分鐘內相鄰的推文合成一則）。內文不用（多半是長文，不是聊天語域）。
- 一則合併後的推文當一則訊息：切成 2–30 字的子句，同一則的第 2 段起前文是前一段，第 1 段空白。
- 同樣套 e2 §2.1 的網址、個資與密鑰、程式碼過濾。
- 一個帳號在一份集合裡最多 20 列（避免少數洗版帳號主導）；超過的照固定種子丟掉。
- 篇的時間取發文時間，只取 2026-08 以前的篇。

### 2.3 S3：M1、M2（公開、私下用）

- 用平台官方的公開 API 抓公開貼文，每個平台最多 3,000 則；抓取程式與參數放 `.agent-local/`，repo 只寫代號與統計。
- 只收繁體中文：OpenCC `s2t` 轉換會改字的貼文丟掉（簡體或混用）。
- 一則貼文一則訊息，切子句與前文照 S2。
- 列檔照私人資料處理（放 repo 外、不交給 subagent 或外部模型、只報統計）。

## 3. 共同處理

- **去重與重疊**：整句和其他任一聊天集、錯字回報、打字測驗、dev302、功能字測試句某一列相同的段拿掉；同一來源裡重複的段留第一個。
- **拿掉暱稱、稱呼與故意的錯字**（維護者決定 1）：
  - main 先讀 S1 的 200 列樣本，整理一份關鍵字表（暱稱、稱呼、故意的錯字），表放私人資料夾。
  - S1：關鍵字命中的列 main 逐列確認，確認的列進校對檔的拿掉清單。
  - S2、S3：關鍵字命中就拿掉（列數太多，不逐列確認）；抽樣校對時看到新的就補進表、重跑一次。
  - 只報列數，不寫出關鍵字。
- **讀音**：`tools/readings.py`；CHECK 的列 main 沒把握就丟。
- **校對**：每份集合抽 10%（固定種子），main 只看正解與讀音、不看候選或分數：
  - 只改明顯的錯字（在／再、的／得）；用字變體不改；沒把握的丟。
  - 報抽樣的錯誤率；PTT、M1、M2 是別人用各種輸入法打的，錯誤率另外各報一個。
  - 錯誤率 > 5% 的來源：停下來回報（正解錯太多，改壞會被高估）。
- **凍結**：校對完寫出列檔與 SHA-256、記進研究紀錄，之後才產生候選。

## 4. 分法（在讀任何內容之前定死）

- **訊息 id**（不依賴檔案裡的位置）：
  | 來源 | id |
  |---|---|
  | Discord | 訊息的 snowflake `ID` |
  | Threads、Facebook 貼文與留言 | 來源名＋時間戳（秒）＋正文的 SHA-256 前 16 位 |
  | PTT 推文 | 看板／文章檔名＋合併後推文在該篇的序號（快照雜湊固定，序號不會變） |
  | M1、M2 | 平台給的貼文 id |
- **S1 的匯出固定**：建集合時把每份匯出檔（Discord 資料包、Meta 匯出）的 SHA-256 記進研究紀錄；`ctune`、`cdev` 與之後每一份 `cjudge-k` 都從同一份凍結的 `clauses.tsv` 切，之後拿到新的匯出也不重切（新匯出要用時另開一片）。
- **桶**：每則訊息依 `sha256(來源 + 訊息 id)` 的第一個位元組分桶，同一則訊息的子句一定在同一桶：
  | 桶（第一個位元組） | S1 | S2 |
  |---|---|---|
  | 0–95 | `ctune` | `ctune` |
  | 96–159 | `cdev` | `cdev` |
  | 160–255 | `cjudge` 池 | `cjudge` 池 |
- **大小**（固定種子 20261027 抽；不夠就全收、照報）：
  - `ctune`：S1 全收（上限 6,000 列）＋S2 6,000 列。
  - `cdev`：S1 全收（上限 5,000 列）＋S2 5,000 列。
  - `cjudge-k`：每份最多 6,000 列，S1 與 S2 各半；S1 從池裡依月份由新到舊取，每份不重複；S2 每份從池裡另抽、不重複。判讀集每月最多建一份。
  - `cmicro`：M1、M2 全收（照報列數），不分桶。
- **每份集合的列都帶來源標記**；表格報整份，另報 S1、S2 各一行。
- 機械計數（不讀內容：時間、頻道類型、伺服器、網址與重疊排除之後的訊息數）先 commit 進研究紀錄，之後分法不改。

## 5. 程式

- `experiments/e2-chateval/build_chatclause.py`：加 `--guild`（§2.1）、`--set ctune|cdev|cjudge`（照 §4 的桶與大小）、輸出列帶來源欄（只在私人列檔裡）。
- `experiments/e2-chateval/build_ptt_chat.py`（新）：§2.2，輸入快照資料夾，輸出同格式的列檔；只印計數。
- `.agent-local/` 裡的 M1、M2 抓取程式（不進 repo）。
- 私人中間檔（`clauses.tsv`，只在私人資料夾）每列加兩欄：Discord 列的頻道 id 與訊息 id（其他來源填來源自己的貼文 id）。這兩個 id 不進任何追蹤的檔案。
- 單元測試：
  - 伺服器篩選（§2.1）；
  - 桶的分法對同一則訊息的子句一致；帳號上限；
  - 訊息 id：合成匯出在前面與後面各多一則訊息時，原有每則訊息的桶不變；
  - 時間窗：合成資料裡放一則 2026-09 的訊息，內文是一個哨兵字串；斷言哨兵不在任何輸出檔，而且網址、個資、斷句函式都沒收到它（把這些函式包一層記錄收到的文字）。拿掉時間窗篩選時這個測試要失敗（突變檢查一次，結果記進研究紀錄）。
- `run_sets.py`、`triage.py`、`judge.py`：集合名加 `ctune`、`cdev`、`cjudge-k`、`cmicro`；舊名照舊可用。到會意 L 為止，舊集合（過濾後的列檔）照舊可以產生新的候選與分數；L 之後不再對舊集合產生新分數。

## 6. 判讀規則的改動（維護者 2026-10-27 決定）

- 出貨標準第 1 條**只留比例那條**：不顯著變差（精確 McNemar p ≥ 0.05 或淨值 ≥ 0），而且改壞÷改對 ≤ 0.6；「改壞 ≤ 26」的絕對數拿掉（它是 `discordtune` 4,958 列上訂的）。L 之後用 `cdev`。
- `CLAUDE.md`「研究」的出貨標準（已改）、`docs/methodology.md` 的集合分層、`docs/kpi.md` 的欄、`docs/iteration-plan.md` 裡寫到舊集合的句子，同一個 PR 一起改。

## 6a. 預算與回滾

- **預算**：§1 的基準表在 GCP 跑（`ctune`、`cdev` 各約 1 萬列、一個設定），上限 2 個 VM 小時；M1、M2 的 API 每個平台最多 50 次請求（每次最多 100 則），照平台公開的速率限制放慢。實際用量記進研究紀錄。
- **回滾**：凍結的集合與私人工作資料夾可以整個刪掉，不影響其他東西；工具的改動都是新增（舊集合名照舊可用），還原這個 PR 就回到原狀。

## 7. 驗收

- 四份集合（`ctune`、`cdev`、`cjudge-1`、`cmicro`）凍結，研究紀錄有 §1 的兩張表。
- 單元測試過；`make test-python` 綠。
- S1 列檔裡沒有指定伺服器以外的 Discord 訊息：用 `clauses.tsv` 的頻道 id 逐列對照該頻道的 `channel.json`，數「`guild.id` 不等於指定 id 或沒有 `guild`」的列，結果必須是 0；數字記進研究紀錄。
- `cjudge-1` 的每月列數表沒有 2026-07 以後的月份。

## 8. 停止條件

- 指定伺服器找不到頻道；任何來源的匯出沒來（那個來源不用、照報，S1 整個沒有才停）。
- 任何來源的校對錯誤率 > 5%；讀音 CHECK > 10%。
- S1 在 `cdev` 的桶裡少於 1,000 列：停下來問（個人文字太少，`cdev` 會幾乎全是 PTT）。
