# SP 第三片：後繼詞優先、其餘相容詞補在後面（離線研究）

SP 第二片（`docs/contracts/sp2-successor-prediction.md`，記為 SP2）量出：候選只用前文歷史詞的後繼詞時，第一鍵和「全部相容詞」持平，但第一個音節打完後明顯較差（discordtune P3 hit@9 43.5% 對 64.4%），縮寫也大約只剩一半。使用者 2026-10-07 決定：維持「後繼詞優先」，再補充來源。這一片量補充之後的做法，給介面契約與核心契約用。只做離線研究，不動核心、殼層、介面，不調參數。

## 1. 做法

- 相容、分數、`v`、模式 P／PA、母體 M／S0／S1／U：全部照 SP2。
- 候選集合 = 第一片的 c 組集合（詞庫裡和查詢相容的全部字串，該模式的解讀）。
- **兩種排序**：
  - **c**（對照，即 SP1 的 c 組）：全部依分數排序。
  - **S（後繼詞優先）**：`v` 的後繼詞依分數排在前面，其餘相容字串依分數接在後面。同一層裡的順序照 SP1 的決定性順序。
  - S 的前段就是 SP2 的 V3；V3 沒有顯示時，S 等於 c 的順序。
- 名次一律悲觀，在各自的排序裡算：同一層同分的對手算在前面；S 的第二層的名次要加上第一層的個數。

## 2. 評測

- 資料、樣本、位置、母體同 SP2。主要結果是母體 M。
- **每個位置**（P 模式 P1–P4；PA 模式 A1、A2）：S 與 c 的 hit@k（k = 1、5、9），分母是全部樣本。
- **省鍵率 KS(k)** 與**第一名翻轉率**：定義同 SP2，名次用各自的排序。
- **配對檢定**：S 對 c 在 P1、P3、A1 的 hit@9，母體 M，每個集合、每個設定一個 McNemar 精確檢定（雙尾）。另報 S 對 V3（SP2 的 P 模式）在 P3 的同一個檢定。
- **時間**：S 的每次查詢 p50／p95。

## 3. 交付與驗收

- **交付**：
  - `experiments/sp/predict3.py`：import `predict.py` 與 `predict2.py` 的函式，參數同 `predict2.py`。只印統計數字。
  - `experiments/sp/test_predict3.py`。
  - `experiments/sp/README.md` 加一節。
  - 研究紀錄由 main 寫。
- **驗收**：
  1. **單元檢查**（手造小詞庫與小模型，期望值手算）：
     - S 的前段是後繼詞、後段是其他相容字串，各層內依分數。
     - S 的悲觀名次在第二層時，要加上第一層的個數。
     - 沒有後繼詞相容時，S 等於 c。
  2. **突變**：
     - S 改成全部依分數排序（等於 c），第一條要失敗。
     - 第二層名次不加第一層的個數，第二條要失敗。
  3. **一致性**（typing76 全部樣本、兩種設定）：每次查詢都比下面三項，任一不符就是停止條件。
     - S 與 c 的候選集合相同。
     - S 前段的字串**集合**等於 `predict2.candidates(idx, units, 模式, succ)` 的字串集合。S 的前段必須由 S 自己的路徑建出（把 c 的候選用 `succ(v)` 過濾），不呼叫 `predict2.candidates`。
     - 前段每個字串的分數和 `predict2.scores(predict2.candidates(...))` 給同一字串的分數逐位元相同（`struct.pack("<d")` 比對）。順序不比：S 依分數排、`candidates` 依詞庫順序。
  4. 公開集合的表寫進 README；discordtune 由 main 跑，只報統計數字；`git diff` 不含私有內容。
- **不在這一片**：介面、核心、組字器、參數調整、其他候選來源。
