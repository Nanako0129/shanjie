  3. **候選窗也加**（維護者 2026-10-23 選「候選窗也一起加」）：開窗時同一段的詞條排序，單字詞條的分數加同一個讀音項。例如打 ㄎㄨㄞˋ 開窗，「會」（ㄎㄨㄞˋ 是它少見的讀音）往後排。
  2. **融合拿掉讀音通道項**（P5 的 ν 項）。常談照現在的出貨留在融合裡，各檔的常談格不變。

## 1. 規則

- **讀音項**：和 R1e 同一份程式（`core/src/reading.rs`，探索分支的 `--reading-decode`）。
  - 路徑上每個單字詞 w 讀 r，加 λ·max(t(r, w), −c)，其中 t 是詞庫分數相對於該字最常見讀音的差。
  - λ 2.0、c 4。
  - 「一」的 ㄧˊ、ㄧˋ 與「不」的 ㄅㄨˊ 算 0。
  - 合併後詞庫分數等於底分 −6.8 的單字讀音，改用 mc 值（多字詞裡用這個讀音的質量）。
  - 多字詞、新詞、詞庫沒有的（讀音, 字）一律算 0。
  - 常數照現在 `reading.rs` 的具名常數，註解寫出處（R1c、R1e）。
- **哪裡生效**：`core/src/lm.rs` 解碼器（`decode_segment_learned` 的單音節詞條）。這是引擎組字、凍結前段之後的解碼、評測 CLI 共用的路徑。
  - 學習加分照舊：讀音項另外再加，學習守門的規則不變。
  - 模糊音（`feat/fuzzy-input`，另一片）合進來時，容錯讀音的詞條也照同一條加讀音項；哪一片先合併，另一片在合併時處理。
- **表**：mc 表與讀音項表在載入詞庫時建一次（引擎與 CLI 同一個函式）。每個詞條的讀音項事先算成和詞條對齊的陣列，解碼時直接取，不再每鍵查字串（`/code-review` 2026-10-23 延後到產品片的那一項）。記憶體量 RSS（§2.4）。
- **候選窗**：`window_list`（與它的預測列、容錯詞部分無關）裡完全吻合的詞條，排序鍵由詞庫分數改成「詞庫分數＋讀音項」（只有單字詞條的讀音項不為 0，所以只有單音節的窗會變）。同分照原本的順序。學習、降權表照舊排在它們原本的位置規則上（讀音項只換掉詞庫分數那一項）。
- **融合**：`core/src/colloquial.rs` 的 `fused_pick`／`guarded_pick` 拿掉 ν 項（`NU`、`channel_of`、`ReadingChannel`）。常談項、軟閘門、各檔的 (α, τ, δ) 不變。重排工作不再帶讀音通道項的詞庫。
- **評測開關與標記**：
  - CLI 與 replay 的 `--no-reading-decode`（只給評測用）：解碼器不加讀音項，融合照產品（沒有 ν 項）。
  - 拿掉 `--reading-decode`（產品預設就是開）、`--no-reading-channel`、`Engine::set_reading_channel`；加 `Engine::set_reading_decode`（只給評測用，不進 `shanjie.h`）。
  - 摘要行的標記：讀音項開著時，設定標記最後加 `+rd`，`+rc` 不再出現。CLI 與 replay 同一條規則。
- **C ABI、殼**：不改。讀音項一律開，沒有使用者設定。

## 2. 驗收

1. **核心等於探索**（R1e 的 30 組，`r1d.py` 的 `ROLES`）：
   - 產品 commit 的 CLI 預設跑法，對應 R1e 每一組的跑法（聊天開帶 `--colloquial-core`，不再需要 `--no-reading-channel`；關的設定不給 `--tinylm`）。
   - 和探索分支 `abd676ab` 那次 R1e 的 rowstats 逐列相同，摘要的 `top1_sha256` 相同（標記會不同：產品沒有 `--reading-decode` 這個選項）。
   - 公開集合在 Mac 跑；私人集合在 GCP，同一種 CPU，跑完刪列。任何一列不同就停。
2. **不變的部分**：
   - `--no-reading-decode` 加上 `--no-reading-channel` 的效果（解碼器不加、融合沒有 ν）在公開集合兩種設定，和 main 帶 `--no-reading-channel` 的那一跑 `top1_sha256` 相同；書面和 main 相同（書面原本就沒有 ν）。
   - golden：會變的逐行列出、說明原因（讀音項改了哪些第一名），其他不動。
3. **測試**：
   - 單元：讀音項的兩個例外、mc、單字以外算 0、事先算好的陣列等於逐字查的結果。
   - 引擎：
     - 一列公開資料，讀音項讓組字區的第一名改變（例如錯字回報第 10 列「版控」）：引擎組字區等於 CLI 的選字，語意校正關也成立；
     - 學習加分的段照舊顯示學到的詞，`guard_skips` 照舊；
     - 融合沒有 ν 項（給一組讀音通道項會改變選字的分數，斷言選字不受影響）。
   - 突變：拿掉變調免扣、拿掉 mc、λ 改 0、融合加回 ν、讀音項只在重排開時加。每個至少讓一個測試以斷言失敗。
4. **延遲與記憶體**：
   - 每鍵延遲照 `timing_typing76_keys` 的量法，p95 ≤ 16 ms，和 main 的倍數一起報。
   - `RerankJob::run` 的 p95 照現行量法，門檻 300 ms。
   - RSS 增加 ≤ 10 MiB。
   - 都在 Linux 機器量（照現行做法），超過就停。
5. **工具**：
   - `tools/triage.py`、`kpi.py`、`bench.py` 接受新的出貨標記，依版本決定：v0.5.0 與之前是 `+rc`，之後是 `+rd`。測試跟著改，`make test-python` 通過。
   - 用新 CLI 跑一次 `tools/triage.py`，聊天與書面都要跑完。
7. **候選窗**（事先固定，看到任何數字之前）：
   - 量法：每一列照正解的斷詞，取每個單字詞的位置，算正解字在「那個音節單獨開窗」時的名次（從 1 起），讀音項加前、加後各一次。只報數字，不含字。
   - 集合：打字測驗、錯字回報（全部 157 列，真人讀音）、dev302、cvtune-clean、discordtune（私人，GCP）。
   - 報：名次變好、變差的位置數，以及「從第一頁（前 9 名）掉出去」的位置數。
   - 閘門：錯字回報與打字測驗（真人讀音）上，從第一頁掉出去的位置數要 0，名次變差的位置數不超過變好的。不過就停下來和維護者討論，不改規則。
   - 〔推論〕工具標讀音的集合（dev302、cvtune、discordtune）幾乎只看得到變好，真人讀音集是唯一看得到「次要讀音被往後排」的地方。
8. **實機**（§0 第 2 點）：繁中 tart 虛擬機，裝本分支的開發版。設定照 `CLAUDE.md`「實機測試與虛擬機」用 `defaults write` 改。前文「否則」之後打「變快」，記錄每一種設定的結果。
