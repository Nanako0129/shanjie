# S7b：比 M 更大的字元語言模型重排（離線研究片）

接續 S7a（`docs/contracts/s7a-tinylm.md`；研究紀錄 2026-10-11）。S7a 的 M（6 層、d 384、1,440 萬參數）通過了做進核心的判斷，S 沒過。**使用者 2026-10-11**：「我希望寧願品質允許大一點的模型開始測吧」——品質優先，可以接受更大的模型，先量更大的。

這一片只回答一件事：**同樣的資料與做法，模型再大，選字有沒有再變好、延遲多少**。不出貨、不改核心；核心實作（Rust 推論、int8 或 float32、保留集）是下一片，用這一片選出的大小。

## 1. 要做到什麼、怎麼看到

- 訓練兩個更大的模型，用 S7a 同一套候選、同一套融合與事先寫死的判斷量，和 n-gram、和 M 比。
- 量 int8 權重夠不夠用（先 M，之後每個大模型），回答「需不需要 FP32」。
- **怎麼看到**：研究紀錄的表格（每個模型 × 兩種設定 × 每個集合一行），加上「大模型對 M」的配對比較，以及延遲與大小。

## 2. 做法（除了模型大小，全部沿用 S7a）

### 2.1 模型

- 架構、字表、訓練文字、批次、學習率排程、種子、一個 epoch，全部和 S7a 相同（`experiments/s7a-tinylm/`，`train.py` 與 `torch_model.py`）。唯一的改動：`torch_model.CONFIGS` 加兩個大小。
  - **L**：8 層、d 512、8 個頭（約 3,000 萬參數）。
  - **XL**：12 層、d 640、10 個頭（約 6,500 萬參數）。
- 訓練文字與 `ids-*.npy` 直接用 188 上 S7a 那份（`%USERPROFILE%\.cache\shanjie\work\s7a`），不重產；第 0 步只核對檔案還在、雜湊和 S7a 的 `charcount.json` 記的相同。
- **順序**：先訓 L。L 在 cvtune＋wikitune 聊天合計（凍結的 α、τ）比 M 的 5,752 多 **≥ 20 列**（約 +0.3 個百分點）才訓 XL；不到就不訓 XL，寫結論。這條只看調參集，事先寫死。
- 不調超參數；不加 epoch（多一個變數就分不出是大小還是資料量的效果）。

### 2.2 打分、融合、判斷

- 公開集合的候選沿用 S7a 的 `dumps/`（雜湊記在研究紀錄），188 用 torch 打分。**錯字回報固定用 S7a 當時的前 66 列**（`eval/dev/user-reported.txt` 之後只在最後面加列；前 66 列的 SHA-256 必須是 `6e338dc129306016…`，不是就停）：`run_sets.py` 對這個集合傳 `--limit 66` 並先核對雜湊，所以 M、L、XL、int8 的錯字回報都是 n = 66，可以配對。Mac 上一致性關卡（numpy 對 torch，cvtune 兩種設定，最大 |ΔLL| < 1e-4）。
- **discordtune**（Mac、numpy、只回數字、用完刪掉）：S7a 的候選與分數已刪，候選在 Mac 上用釘住的 model-v5＋classes-v3（`run_sets.py dumps` 會核對雜湊）**重新產生一次**，M、L、XL 都用這同一份。
- 融合格點、選法（只用 cvtune＋wikitune 選 α、τ）、§4 的條件，和 S7a 完全相同（`fusegrid.py`）。
- **M 的重現關卡**：M 用 S7a 的 `tinylm-M.npz`（SHA-256 `32308122782d3c5a…`），α、τ 用 S7a 凍結的值（聊天 0.7／2、書面 0.7／2，不重選），在重新產生的 discordtune 候選上打分；它的兩列必須等於 S7a 記的（聊天 n 4,958、top1 4,209 → 4,276；書面 4,143 → 4,223）。不等（例如私有檔變了）就停，回報，不做任何對 M 的比較。
- **對 n-gram 的判斷**：每個大模型各自照 S7a §4（discordtune 聊天 Δtop1 ≥ +1.0 個百分點、精確 McNemar p < 0.05、Δtop1 區間不含 0、ΔCER ≤ 0；其他集合沒有「淨值為負而且 p < 0.05」的格）。
- **對 M 的比較**（事先寫死）：discordtune 聊天，大模型重排後的結果對 M 重排後的結果，`tools/evalstats.py compare`（M 為基準）。
  - **選大模型**：大模型通過對 n-gram 的判斷，而且對 M 的 Δtop1 > 0、精確 McNemar p < 0.05。
  - 大模型通過對 n-gram 的判斷、對 M 的 Δtop1 > 0 但 p ≥ 0.05：記為「比 M 多對但不顯著」，**由使用者決定**（品質與大小、延遲的取捨），不自動選。
  - 其他情況：維持 M。
  - **L、XL 結果不同時**（XL 沒訓就只看 L）：結論取「選大模型」的模型裡最大的那個；L 與 XL 都是「選大模型」時，XL 對 L 再用同一條規則（XL 顯著勝過 L → XL；XL 多對但不顯著 → 由使用者在 L、XL 之間決定；其他 → L）。沒有任何「選大模型」、但有「多對但不顯著」的 → 由使用者決定（列出這些模型與 M）。兩個都是「維持 M」→ M。

### 2.3 int8 夠不夠用（使用者 2026-10-11：「已經訓練好的可以先看看 int8 效果有沒有需要 FP32」）

- 先做 M（已訓練好、不必等 188），之後每個大模型照做。S 沒過 S7a §4，不量。
- **量化方式**：和 `latency.py` 的 int8 複本相同（矩陣每列對稱 int8、float32 縮放；向量照舊 float32），還原成浮點後用同一個 numpy 前向打分，所以量的是「權重 int8」的影響；核心片的 Rust 版若另外把活化值也量化，要再量一次。
- **α、τ 固定用該模型 fp32 凍結的值**（M：聊天 0.7／2、書面 0.7／2），不重選，只看量化本身。
- 集合：cvtune、wikitune、dev302、打字測驗、錯字回報、discordtune（discordtune 用 §2.2 重新產生的同一份候選），兩種設定。
- **判斷（事先寫死）**：int8 夠用＝同時成立：(a) int8 對 n-gram 照 S7a §4 仍通過；(b) int8 對 fp32（fp32 為基準，`evalstats compare`）在每個集合、每種設定都沒有「淨值為負而且 p < 0.05」的格。任何一條不成立就記為「需要 FP32」。float16 不在這一片。

### 2.4 延遲與大小

- 照 S7a：`latency.py`（Mac numpy，8 個候選 × 17 字一批，200 次，float32 與 float64 的 p50／p95），以及 npz（float32）與 int8 複本的大小。
- 延遲只報告，不自動排除；numpy float32 p95 > 150 ms 的模型標明「要在核心片用 Rust 實測」。

## 3. 驗收

1. 第 0 步：S7a 的訓練文字與 ids 還在、雜湊相同；`tinylm-M.npz` 的 SHA-256 等於 §2.2 記的；CONFIGS 的參數量與 §2.1 相符（單元測試）；M 的重現關卡通過（§2.2）。
2. 訓練：每個模型的參數量、步數、最終損失、時間；不發散。
3. 一致性關卡：每個新模型 cvtune 兩種設定最大 |ΔLL| < 1e-4。
4. 表格與判斷：每個模型 × 兩種設定 × 六個集合（cvtune、wikitune、dev302、打字測驗、錯字回報前 66 列、discordtune），`evalstats` 同一張表；凍結的 α、τ；對 n-gram 的判斷逐項 PASS／FAIL；對 M 的配對比較（聊天、書面各一行）。
5. int8 的判斷（§2.3）：每個量的模型，int8 對 n-gram 的 §4 逐項、int8 對 fp32 的表（每個集合 × 兩種設定），與結論「int8 夠用」或「需要 FP32」。
6. 延遲與大小（§2.4）。
7. 研究紀錄、本契約的結果一節、PLAN 的 S7 狀態行；`make test` 全綠；fresh verifier 確認第 3、4 項可以從檔案重現（discordtune 那幾行照 S7a 的做法核對內部一致）。

## 4. 範圍外、停止條件、預算、限制

- **範圍外**：Rust 推論與出貨；活化值量化與 float16 的準確度（核心片量）；保留集（核心片由 fresh verifier 跑）；改資料、加 epoch、調超參數。
- **停止條件**：M 的重現關卡不過（§2.2）；錯字回報前 66 列的雜湊不符；訓練發散或 8 GB GPU 記憶體不夠（不改批次大小、也不改成梯度累積，回報）；輸入雜湊不符；一致性關卡 ≥ 1e-4；前文接線的檢查失敗；L 對 M 的調參集增幅不到 20 列（不訓 XL，寫結論）。
- **預算**：L 一次（約 3.5 小時，推論）、XL 一次（約 8 小時，推論）；程式改動只有 CONFIGS 與它的測試、`run_sets.py` 對錯字回報傳 `--limit 66` 並核對前 66 列的雜湊（§2.2），以及 §2.3 用的小工具 `experiments/s7a-tinylm/int8check.py`（產生 int8 還原權重；用固定的 α、τ 重排並寫 rowstats，沿用 `fusegrid` 的 `pick` 與 `rowstats`）與它的測試（main 做）。
- **限制**：188 綁 P-core、絕對路徑；discordtune 只在 Mac 用 numpy、只回數字、用完刪除；不讀 `eval/holdout`；agent 不讀 `~/side-project/shanjie-private`、學習檔、`~/Library`、鑰匙圈。

這一片只改 `torch_model.CONFIGS`（加 L、XL）、`int8check.py` 與它們的測試，以及文件；revert 那個 commit 即可。不出貨，使用者端不受影響；權重與分數只在 188 與 Mac 的 `~/.cache/shanjie/work/`，不進 repo。

## 6. 結果（2026-10-11）

- **第 0 步**：M 的重現關卡兩列都和 S7a 相同；錯字回報前 66 列雜湊相符。`charcount.json` 沒有 ids 的雜湊，改核對 ids 的修改時間、L 訓練記錄的字表／片段／步數和 M 相同，並記下現在的雜湊（研究紀錄）。
- **M 的 int8**：int8 夠用（對 n-gram 的 §4 仍過；對 fp32 的 12 格都沒有顯著淨負）。
- **L**：一致性 1.26e-5；聊天 α 2、τ 2（格點最大值）、書面 α 1、τ 2；**§4 沒過**（discordtune 聊天 −30 列，p = 0.24）；對 M discordtune 聊天 −97（p < 0.0001）、書面打平。依 §2.2：**維持 M**。L8 對 L 沒有顯著差的格。延遲（numpy float32）p95 47.7 ms；int8 複本 30.6 MB。
- **XL**：門檻（L 調參集多 52 列）觸發，開始訓練後碰到停止條件（8 GB GPU 放不下，專用 7.5 GB＋共享 13 GB，約 22.5 小時）。使用者決定停掉 XL、先修 α 的選法，下一片再決定 XL。
- **結論**：S7b 選 M（int8）。表格與讀法在研究紀錄同日 S7b 一節。
