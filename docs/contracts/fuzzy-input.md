## 0. 起因

- 維護者 2026-10-14（選擇題）：研究之後下一片做「模糊音（ㄣㄥ、ㄓㄗ、ㄔㄘ、ㄕㄙ），預設關」。
- 維護者同日：「模糊輸入我覺得很必要的是鄰近模糊輸入，這片可以同時研究一下嗎？」——鄰鍵打錯也放進這一片。
- 研究的數字（dev299＋typing76，375 句；救回率的分母是「注入後完全吻合解錯」的列）：
  - 模糊音（G2，δ＝1）：合法讀音第一名救回 91–95%；dev299、typing76 乾淨輸入改壞 0；調參 1,000 列改壞 3；Python 延遲約 1.4 倍。
  - 鄰鍵（研究的 G0 是「整句完全吻合解不出來時，句子裡每個音節都可以用容錯」，比這一片只對詞庫沒有的音節容錯寬，所以研究的數字是**上限參考**，不是這一片的目標）：打錯多半變成**不合法讀音**（p＝0.05 時 140 列不合法、94 列合法）。不合法讀音今天在輸入時就被 s3a §2「詞庫沒有的音節不收」擋下；只在完全吻合解不出來時才容錯（G0），第一名救回 84%（p＝0.05）／65%（0.1）／32%（0.2），而且**構造上不會改壞打對的輸入**（打對的音節都在詞庫裡，走不到這條路）。合法讀音的鄰鍵（G2，δ＝2）在 typing76 改壞 4／76，風險在這一類。

## 1. 要做到什麼、怎麼看到

- 設定視窗「模糊輸入」，**預設全關**：
  - **模糊音**：四對各自一個勾選（ㄣ／ㄥ、ㄓ／ㄗ、ㄔ／ㄘ、ㄕ／ㄙ）。開著時，每個區段除了完全吻合的詞條，再查「把那一對換掉」得到的讀音的詞條（每個詞最多一個音節用容錯），容錯的詞條分數減 δ＝1（研究選的值，log10）。
  - **鄰鍵打錯**（只做 G0）：開著時，完成音節時若詞庫沒有這個音節，但照欄位規則把**一個**注音鍵換成同一列左右的鄰鍵（研究的鍵盤定義與欄位規則，`docs/contracts/fuzzy-research.md` §2）能得到詞庫有的音節，就**收下這個音節**（組字區照常顯示解碼出的字）；解碼時這個音節只用那些替代讀音的詞條，分數減 δ＝2。沒有任何替代讀音時照舊不收。音節在詞庫裡時完全不走這條（打對的輸入不受影響）。
- **誰、怎麼看到**：
  - 維護者實機（關掉時一切照舊；打開後）：模糊音開 ㄓ／ㄗ，打 `ㄗ ㄉㄠˋ`（想打「知道」）第一名是「知道」；鄰鍵開，故意把「謝謝」的某個鍵打成鄰鍵、造出詞庫沒有的音節，仍得到「謝謝」（實際按鍵由 main 從鍵盤定義挑一組、寫進 PR）。
  - 量測（§3）證明乾淨輸入不退步、延遲在範圍內。

## 2. 實作

### 2.1 核心（Rust）

- **容錯表**：載入詞庫時，從詞庫的音節集合建兩張表（和研究的 `Tolerance` 同一個定義）：模糊音（每對一個位元，查「正規化後相同」的其他音節）、鄰鍵（反向：觀察到的音節 → 經欄位規則可能是哪些詞庫音節）。只建一次；記憶體增量記錄在研究紀錄。
- **收下音節**（`finish_syllable`，s3a §2）：鄰鍵開著、**語言模型已載入、而且是標準排列**時（鄰鍵表只照標準排列的鍵盤定義；**倚天排列下第 4 位元沒有作用**，詞庫沒有的音節照舊不收），詞庫沒有但有鄰鍵替代讀音的音節才收下（存打的讀音）；沒有語言模型時照舊不收（`decode_beam` 的路徑不改）。
- **解碼**：`core/src/lm.rs` `decode_segment_learned` 的區段查詢（`base.find(&ids[i - l..i])`）：
  - 模糊音開著時，除了原本的查詢，區段裡每個音節輪流換成它的模糊音替代讀音各查一次（每個詞最多一個音節用容錯）；查到、而且不在完全吻合詞條裡的詞，分數減 δ＝1。同一個詞照最好的那條。
  - **詞庫沒有的音節**：解碼**一律**（不看鄰鍵開關）用它的鄰鍵替代讀音查，詞條分數減 δ＝2；開關只管 `finish_syllable` 收不收。所以收下之後再把鄰鍵關掉，組字區裡已收下的音節照樣解得出來，不會進內部錯誤。
- **候選窗**：某一段（游標處開窗時的那個範圍）的清單＝完全吻合的詞條，後面接容錯得到的詞（模糊音開著時的模糊音詞、含詞庫沒有的音節時的鄰鍵詞），照分數排、去掉和前面重複的。**選了容錯得到的詞**：把 `syls` 的那一段換成那個詞的詞庫讀音（和 `choose_pred` 換讀音的做法相同），再照一般選詞固定；之後的重算、`best_lp_delta` 與學習都用詞庫讀音。只含詞庫沒有的音節、又沒有任何替代讀音的段，不會出現在組字區（收不下來）。
- **學習**：查詢（`has_reading`、`lookup`）對容錯的詞用它的詞庫讀音；寫入只發生在固定的詞上，而候選窗選了容錯的詞時 `syls` 已換成詞庫讀音（上一條），所以學到的記錄也是詞庫讀音；理由：同一個詞下次打對時要能沿用。
- **設定 ABI**：`shanjie_engine_set_fuzzy(engine, uint32_t flags, ShanjieOutput **out)`：位元 0–3 是四對模糊音、位元 4 是鄰鍵；其他位元非 0 回 2、狀態不變；回傳碼與快照照 `shanjie_engine_set_english` 的慣例。引擎預設 0。`core/include/shanjie.h` 與 `docs/contracts/s3a.md` 的 ABI 一節同步。
- **s3a**：§2「詞庫沒有的音節不收」加上鄰鍵的例外（指到本契約 §1）；按鍵規則表不變（只有完成音節的結果不同）。

### 2.2 殼

- UserDefaults 鍵 `fuzzyFlags`（沒有值＝0），每次建引擎時送進去；設定視窗加「模糊輸入」一節（四個勾選＋鄰鍵一個勾選），和既有設定同一種樣式；**排列選倚天時鄰鍵的勾選反灰**（值保留，切回標準排列又生效）。選單不加項目。

### 2.3 CLI 與參考實作

- `shanjie-eval` 加 `--fuzzy <flags>`（同 ABI 的位元），摘要行加標記 `+fz:<flags>`（不給時輸出不變）；可以和 `--set holdout`、`--context`、`--packs`、`--tinylm` 一起用。給了 `--fuzzy` 時，解不出路徑的列算錯（第一名是空的）、繼續跑下一列，不中止整個集合。
- 研究的 `experiments/fuzzy/` 既有的檔不改；main 新增一支 `experiments/fuzzy/export_rows.py`：用研究的注入規則與種子，把注入後的讀音寫成 CLI 的 `--rows` 格式（`前文|句子|讀音`），只用公開集合。
- 解碼一律用鄰鍵替代讀音（§2.1），所以 CLI 不給 `--fuzzy`（或給 0）時，含詞庫沒有的音節、而且它有替代讀音的列也解得出來，不再中止；`export_rows.py --score` 因此把不合法那一類的「不容錯」一律算錯（和研究的精確解碼器一樣），只對合法讀音那一類讀 `--fuzzy 0` 的 rowstats。

### 2.1b 實作時定下的細節（executor 的決定，main 確認）

- **候選窗的順序**：所有長度的完全吻合詞條照舊排前面，容錯得到的詞接在後面（讀音長的先、同一個讀音裡照分數）。
- **鄰鍵收下的條件**另加一項：這個音節沒有被收過（不在詞庫的音節表裡）。（原本還有「至少一個替代讀音有單音節詞條」一項；詞庫 1,417 個音節都有單音節詞條，這一項永遠為真，2026-10-23 刪掉；這個前提由測試 `engine_fuzzy::every_syllable_has_a_single_entry` 守著：載入含詞包的詞庫，每個音節都要有單音節詞條。）
- **模糊音只用在全是詞庫音節的區段**；含詞庫沒有的音節的區段只用鄰鍵替代讀音。所以模糊音換出詞庫沒有的音節（例如把 ㄓㄨㄚ 打成 ㄗㄨㄚ）時，鄰鍵開著才可能收下、而且只走鄰鍵；這一類在 §3.1 的救回數是 0（研究的 G2 是 12／13，dev299、p＝0.1），留給之後一片。
- **`set_fuzzy`** 重算組字區並回傳那個快照（和 `set_demote` 一樣），不是 `set_english` 的原樣快照；殼在建引擎時與設定改變時各送一次。

### 2.4 鄰鍵的合法讀音（G2）：只研究、不出貨

- 在 `experiments/fuzzy/` 上（Python 參考實作，188 跑）試兩個降低改壞的方向：δ 加大（3、4、5）與只用一個方向的鄰鍵（研究是同一列左右各一鍵；這裡另試「只往左」「只往右」兩個子集。手頭沒有使用者真實打錯的分布，所以只用鍵盤幾何）。量法與研究相同（`grid.py`，tune 1,000 列選 δ、dev299＋typing76 報），只記錄。**出貨門檻**（另開一片才出貨）：dev299 與 typing76 乾淨輸入改壞 0、tune 改壞 ≤ 0.5%、合法讀音第一名救回 ≥ 50%（p＝0.1）。

### 3.6 語意校正不換成容錯詞（修訂二，2026-10-23 登記，在任何修訂二的數字之前）

- **起因**：§3.5 選中 δ 2.5，照登記不過：dev302 聊天 0／2。兩列的 n-gram 第一名都已經是打的讀音，改壞都發生在語意校正把前 8 名裡的容錯詞換上去（第 217 列「身為」、第 298 列「書」；會意在 298 列其實偏好「酥」，換成「書」的是常談項〔推論〕）。語意校正這一層看不到讀音。0c-ime v0.2.5 的做法（只讀，研究紀錄同日）：重排的候選只從打的讀音解出來，近音不進重排。維護者選「照 0c 的自動模式」。
- **規則**（模糊音開著時；鄰鍵的規則不變）：
  - **容錯詞**＝詞條的來源（`lm.rs` 的 `Source`）是一段**不含詞庫沒有的音節**的區段的模糊音替代讀音（`names.is_some()`，而且那一段的 id 都不是 `u32::MAX`）。解碼時把這個標記明確帶在路徑上的每個詞，**不從 δ、`best_lp` 或分數推斷**。鄰鍵讀音的詞、學到的新詞、打的讀音本身的詞（有沒有降權都一樣）都不是容錯詞；從模糊音替代讀音查到、又有學習加分的詞仍是容錯詞。一條路徑只要有一個容錯詞就是「容錯路徑」。
  - **過濾用的清單**：解碼器回傳的 n-best（每個字面一條路徑）。不重新解碼，也不替同一個字面另找一條不是容錯的路徑。
  - **n-gram 第一名是容錯路徑**（救回）：那一段不送語意校正，組字區照 n-gram 第一名；`guard_skips` 之外另記一個計數 `fuzzy_skips`。
  - **n-gram 第一名不是容錯路徑**：送語意校正的候選＝n-best 依原本順序、跳過容錯路徑之後的前 8 條；不足 8 條就全部（照 n-best 順序）。錨點仍是 n-gram 第一名（`Choice.expect` 不變）。
  - **引擎與 CLI 用同一個核心函式**決定「這段跳不跳過」與「候選池」。`shanjie-eval` 在 `--fuzzy` 含模糊音位元時照同一條規則：第一名是容錯路徑就不重排；否則對池子重排，選中的候選對應回原本 n-best 的索引，`ok`、`--tinylm-scores` 的 `c` 欄、`--dump` 都用原本的索引。`--tinylm-scores` 的 `ng`／`ok`／`ed`／`ll` 欄列的是池子（照池子的順序），另加 `idx` 欄寫池子各條在原本 n-best 的索引。
  - δ 固定 2.5（§3.5 選出的值），寫進 `fuzzy::DELTA_SOUND`。
  - 學習照 §2.1 不變。
- **判讀**（照 §3.2 原本的閘門）：
  - **指令**：§3.5 的設定，也就是 §3.2 那條指令，聊天另加 `--colloquial-core data/lm/colloquial.sjlm`（讀音通道項照出貨開著）；基準是同一條指令不給 `--fuzzy`。聊天每一行摘要的標記都要有 `+colloq:<sha8>+rc` 與 `+fz:15`。
  - dev302、打字測驗、錯字回報兩種設定，`--fuzzy 15` 對全關改壞 0。
  - cvtune-clean、wikitune-clean 兩種設定，乾淨輸入改壞率 ≤ 0.5%（GCP）。
  - 另報、不擋：§3.5 同一份注入列上合法讀音的 `rescued@1`，和 §3.5 的 δ 2.5 那一格並列（看這條規則少救回多少）。
  - 不過就停下來和維護者討論。
- **測試**（加進 §3.4，每條都要有會讓它失敗的突變）：
  - 標記：(a) 降權後 delta 剛好 2.5 的打的讀音詞，不標成容錯詞；(b) 鄰鍵讀音的詞不標；(c) 模糊音替代讀音的詞要標。突變「用 delta > 0 推斷」讓 (a) 失敗；突變「所有容錯來源都標」讓 (b) 失敗。
  - 引擎（模糊音 15、有小模型）：(d) n-gram 第一名是打的讀音、前 8 名裡有一條容錯路徑 → 那條不在工作的候選裡；不是容錯的路徑不足 8 條時，池子是它們全部、照 n-best 順序；(e) n-gram 第一名是容錯路徑 → 那一段沒有重排工作、`fuzzy_skips` 是 1、組字區是 n-gram 第一名。拿掉過濾讓 (d) 失敗；拿掉跳過讓 (e) 失敗。
  - 引擎與 CLI 一致：(f) 同一份輸入（`--fuzzy 15`）分別走引擎的工作與 CLI 的選字路徑，候選清單與選字相同；一例是打的讀音第一名、前 8 名裡有容錯路徑，一例是容錯路徑第一名。任一邊拿掉過濾都讓測試失敗。
- **已看過的**：§3.5 的全部數字、dev302 第 217、298 列在 δ 2.5 的候選與分數。
- **預算**：GCP ≤ 1 小時。

### 3.4 測試

- Rust：容錯表對幾個手寫音節正確（模糊音每一對、鄰鍵照欄位規則，含研究的例子 ㄇㄧㄥ→ㄇㄥ）；設定全關時 `decode` 的結果與現在逐位元組相同（golden 不變）；模糊音開時「ㄗ ㄉㄠˋ」第一名是「知道」；鄰鍵開時一個詞庫沒有的音節被收下並解出替代讀音的詞、關時照舊不收；**沒有語言模型時**鄰鍵開也不收（不會進內部錯誤）；**收下後把鄰鍵關掉**：組字區照樣顯示、重算不出錯；**逐音節**：一句裡有一個詞庫沒有的音節時，只有那個音節用替代讀音，其他打錯但合法的音節不容錯；候選窗列出容錯的詞（排在完全吻合之後），選了以後 `syls` 那一段換成詞庫讀音、送出後學習檔記的是詞庫讀音（按鍵序列：開模糊音 ㄓ／ㄗ → 打 ㄗ ㄉㄠˋ → 開窗選「知道」→ Enter → 讀學習記錄）；**倚天排列**：旗標 16 的倚天引擎，遇到一個標準排列鄰鍵表會收下的詞庫沒有的音節，照舊不收（突變：拿掉排列的檢查 → 斷言失敗）；ABI 的回傳碼與快照。每條至少一個會讓它失敗的突變。
- Swift：設定存取、建引擎時送出旗標、設定視窗的勾選。
- `make test-rust` 在 188 WSL、`make test-swift` 在 Mac，CI 全綠。

## 4. 範圍外

整串輸入（另一片）；聲調容錯；倚天排列；從使用者的打字學打錯分布；鄰鍵 G2 的出貨（§2.4 只研究）；多於一個音節用容錯的詞。

## 5. 停止條件

- §3.2 鄰鍵開時 `top1_sha256` 有任何不同；模糊音全開時 dev302、typing76、錯字回報有改壞，或 tune 改壞率 > 0.5%；保留集淨值 < 0（發版前的基準測試才量，見 §3.2）。
- §3.3 延遲倍數 > 2 或記憶體 > 20 MiB。
- §3.1 差超過 3 列而查不出原因。
