# 組字途中行矩形突然跳走時不跟（候選列位置防護）

## 1. 起因與目標

- **維護者回報（2026-10-13）**：在 Orca（`com.stablyai.orca` 1.4.224，Electron，終端機裡跑 Claude Code）打字時，候選列飄到螢幕中間；CPU 吃滿、Claude Code 的畫面正在更新時才會發生。
- **量到的**（診斷版，`/tmp/shanjie-rect-trace.log`，只記數字與 bundle ID；分支 `diag/orca-rect` 不出貨）：
  - 553 次詢問裡，同一段組字中前後兩次定位的 y 差：Orca 364 次是 0 或 1 pt，Discord 338 次都是 0。
  - 用戶端回報的行高（追蹤記的矩形是「寬 x 高」）：Orca 434 個非零矩形是 22 pt（411）或 23 pt（23），Discord 528 個都是 21 pt。
  - 有三段，Orca 自己回報的行矩形在組字途中突然跳走（x, y, 寬 x 高）：(434,88 1x22) → (472,319 1x22)（y +231）；(572,88 1x22) → (1002,928 1x22)（+840）→ (1018,928 1x22) → (2504,739 1x22)（−189）；下一次組字改變時回到 (622,88 1x22)（−651）。
  - 跳走之後，30 ms 與 150 ms 後再問同一個字，Orca 回的仍是跳走的位置。最新的字回報「沒有位置」（原點 0,0）時，`lineRect` 往前找到的也是跳走的那個。
  - 所以候選列跑到中間是**用戶端回報的位置**造成的，不是 §2.3 的「沒有行矩形時用上一次的」。推論（沒量過）：Claude Code 重畫時把終端機游標移到別處，Orca 回報的是游標當下的位置；負載高時重畫慢，比較容易問在那個時候。
- **為什麼要在善解處理**：維護者說，善解有即時預測，打字時候選列一直在，所以很明顯；蘋果注音只在選字時出現，很難觸發，拿來對照沒有意義（2026-10-13）。
- **目標**：同一段組字裡，用戶端回報的行矩形如果離上一個採用的位置太遠，就不採用，候選列留在上一個位置；正常的移動（同一行往右、換到下一行）照常跟。

## 2. 做法

### 2.1 規則（純函式，可以單元測試）

`PanelPlacement.steadyLine(_ new: NSRect?, anchor: NSRect?) -> NSRect?`：

- `anchor` 是這一段組字裡**上一個採用的**行矩形（不是上一個回報的）。
- `new` 是 nil：回傳 nil（照 §2.3 現行規則，由 `topLeft` 用記住的行矩形）。
- `anchor` 是 nil（這段組字第一次拿到行矩形）：回傳 `new`。
- 兩者都有：`abs(new.minY − anchor.minY) > 2 × max(anchor.height, 16)` 時回傳 `anchor`（不採用），否則回傳 `new`。
  - 依據：上面量到的正常移動是 0–1 pt，跳走是 189–840 pt。Orca 的行高是 22 或 23 pt，門檻是 44 或 46 pt；Discord 21 pt 時是 42 pt。所以門檻在 22 pt 以上（換到下一行、差一行高照常採用）、189 pt 以下（量到的跳走都擋得住）。
  - 16 是 `lineRect` 起始矩形的邊長，用戶端給的高度是 0 時的下限。
  - 只看 y。x 不看：換行時 x 本來就會大幅往左移。

### 2.2 接到殼裡

- `Shell` 多記 `lineAnchor: NSRect?`。
- `Session.apply` 從 `client.lineRect(cursor:)` 拿到矩形之後，先過 `steadyLine(_, anchor: shell.lineAnchor)`，把結果存進 `lineCache`、傳給 `showCandidates`；結果不是 nil 時更新 `lineAnchor`。
- `lineAnchor` 的壽命是**一段組字**：組字結束（`composing` 變成 false：送字、清掉、核心失敗、`discardOrphan`）或擁有者換掉時清掉。候選列在組字途中暫時隱藏（候選是空的）時**不**清。
- `lineCache` 不變（同樣的組字與游標就不再問用戶端）。
- 不改 `lineRect` 往前找的規則、`topLeft` 的夾回與上下規則、`lastLine`。

## 3. 怎麼看到它有效

- **純函式**（`PanelPlacementTests`）：
  1. 用量到的三段數字（含高度）重播：(434,88 1x22) 之後的 (472,319 1x22) 不採用、回傳 (434,88)；(572,88 1x22) 之後的 (1002,928 1x22)、(1018,928 1x22)、(2504,739 1x22) 都不採用；之後 (622,88 1x22) 採用。
  2. 正常移動照常：同一行往右（y 差 0、1）、換到下一行（y 差 22）、連續換兩次行（每次差 22）都採用。
  3. 第一次拿到的矩形一定採用；`new` 是 nil 時回傳 nil；高度是 0 的 anchor 用 16 當行高。
- **接線**（`ShellTests`，用現有的 `FakeClient.line` 與 `FakePanel.lineRect`）：
  4. 同一段組字裡，`client.line` 設成輸入列 (434,88 1x22)、按一個鍵；改成 (472,319 1x22)、再按一個鍵：`panel.lineRect` 仍是 (434,88)。
  5. 接著只移動選擇（組字與游標不變，走 `lineCache`）：`panel.lineRect` 仍是 (434,88)。
  6. 送字之後的下一段組字：先在第一段裡確認遠的矩形被擋（同第 4 項），送字，再讓新組字的第一個矩形是 (472,319 1x22)：`panel.lineRect` 是 (472,319)（`lineAnchor` 有清掉）。
  7. 組字途中候選列隱藏再出現（候選暫時是空的）：再給遠的矩形仍被擋（`lineAnchor` 沒清）。
- **突變**：
  - A：`steadyLine` 直接回傳 `new`，第 1 項要失敗；
  - B：`Session.apply` 照算 `steadyLine`、更新 `lineAnchor`，但把 `client.lineRect` 的原值交給 `lineCache` 與 `showCandidates`，第 4 項要失敗。
- **實機**（維護者，裝診斷版：這一片的修正加上矩形追蹤，追蹤在不採用時多記一行 `rejected`）：
  - Orca 裡的 Claude Code，畫面更新、負載高時打字：候選列不再跑到中間；追蹤裡有 `rejected`，而且那幾次的定位留在輸入列。
  - 一般 App（備忘錄或 Discord）：打一段長的組字，讓它在窄視窗裡換行，候選列跟到下一行。

## 4. 驗收

1. §3 的測試都過，`make test` 過；突變 A 讓第 1 項失敗，突變 B 讓第 4 項失敗（看斷言失敗，不是編譯錯誤）。
2. 實機兩項都由維護者確認。
3. 文件照 §2.3 更新。

## 5. 停止條件

- 實機或測試發現正常情況在一次按鍵內移動超過兩行（例如在組字中間按鍵把游標移回好幾行前的開頭），而且這種情況常見：停下回報，不自己放寬門檻。
- 實機裝上之後，Orca 仍然跑到中間，而且追蹤顯示那幾次沒有被擋（例如第一次拿到的矩形就是錯的）：停下回報。

## 6. 範圍外與已知限制

- 修 Orca 或 Claude Code；回報上游。
- x 方向的防護；換螢幕的判斷。
- 已知限制：組字途中拖動視窗、或游標在一次按鍵內跳過兩行以上，候選列會留在原處，直到這段組字結束。
- 診斷用的矩形追蹤不進 repo、不出貨。
