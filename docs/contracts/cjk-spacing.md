# 中英文之間自動加空格（俗稱「盤古之白」）

狀態：READY（2026-10-18，plan-verifier 第一次審查）。修訂一（2026-10-19，`/code-review` 之後）：p 改存在每個 session、組字開始與直通鍵時清掉；漢字判斷看第一個 scalar；store 參數必填；已知限制與實機驗收補齊。

## 0. 起因與名稱

- Discord 回饋串 2026-10-18：三位使用者想要漢字和英文、數字之間自動有空格，其中一位建議做成設定開關。維護者同日決定開這一片，並用選擇題決定兩件事：英文與數字都加；送出時開頭也看游標前一個字補空格。
- 名稱：「盤古之白」出自 pangu.js 的 README，是半開玩笑的暱稱，不是正式術語。W3C《中文排版需求》（clreq）講的「中西文間距」是排版上約四分之一字寬的間距；輸入法只能插入真的空白字元，做不到那種窄間距。所以設定項目用直白的名稱「中英文之間自動加空格」，說明文字再提「盤古之白」。

## 1. 規則（殼 `ShanjieKit`；核心不改）

- **只改善解自己送出的文字**：也就是 `Session.apply(o)` 的 `o.commit`。殼呼叫 `client.insertText` 的只有這一處（`s3b.md`「`commit` 非空」那一條）。
  - 核心送出、學習、前文用的字串都不變：學習用的是核心內部的送出文字，殼加的空白不進核心。
  - 組字區顯示的 marked text 不加空白，只有送出時加。
- **字元分類**：
  - 漢字：一個字（grapheme）的**第一個 scalar** 符合 `LeftContext.isHan`，和核心逐 scalar 判斷的 `is_han` 一致；所以帶異體字選擇符（U+FE00–FE0F、U+E0100–E01EF）的漢字也算漢字。
  - 半形英數：ASCII `A–Z`、`a–z`、`0–9`。
  - 其他字元（全形與半形標點、符號、空白、注音符號、全形英數、emoji 等）一律不觸發，也不會在它們旁邊加空白。
- **送出的文字裡面**：一個漢字和一個半形英數直接相鄰時（兩個方向都算），中間插入一個半形空白 U+0020。例如：
  - 「我用claude寫」變成「我用 claude 寫」。
  - 「2026下午3點」變成「2026 下午 3 點」。
  - 已經有空白的（例如中英混打打出的「我用 claude 寫」）不變。
  - 「（2026）」、「，claude」也不變：標點旁邊不加。
- **開頭**：令 p 是這次送出之前、游標前面的最後一個字元。p 是半形英數而送出文字的第一個字元是漢字，或 p 是漢字而第一個字元是半形英數時，在開頭補一個空白。p 是「無」時開頭不補。
- **p 的生命週期**（修訂一）：p 存在每個輸入 session 自己的欄位（`Session`），不放在共用的 `Shell`。
  - **組字開始時一律先清成「無」**：`Session.send` 在殼不在組字中（`!shell.composing`）時先把 p 清掉，不管這個鍵帶不帶修飾鍵（例如 Ctrl+\ 開始組字也會清）。
  - 接著，如果這個鍵照現在的規則會讀 client（字元鍵、沒有 Control 等修飾鍵、學習沒有暫停），就用**同一次讀取**的原始文字最後一個字元當 p。讀取的函式把漢字尾巴和這個字元一起回傳，由 `send` 寫進 `Session`；讀取的函式本身不改任何狀態。讀不到時（沒有插入點、client 還留著 marked text、範圍長度是 0）或學習暫停時，p 維持「無」。
  - **每次送出之後**，p 改成這次送出（加空白之後）的最後一個字元。所以同一個組字分兩次送出（例如碰到 128 個單位的上限（原本 40）），或送出後直接從預測列選字送出，都用上一次送出的最後一個字判斷。
  - **核心回「不處理」的鍵（直通給 App）一律把 p 清成「無」**：直通的鍵可能移動游標或插入文字（方向鍵、Cmd+V、數字鍵盤等），之後殼不知道游標前是什麼。
  - `deactivateServer` 與換擁有者時清成「無」。
- **結尾**：不加空白，因為不知道接下來會打什麼。
  - 已知限制（修訂一補齊）：
    - 在 Mac 上切換中英文用的是系統的 Caps Lock（`s3b.md` §3），切到英文時善解不在作用中。之後在其他輸入法打的英文，前面不會有空白。反過來的情況（先用 ABC 打英文，再切回善解打中文）由上面的「開頭」處理。
    - 核心直通給 App 的鍵（數字鍵盤的數字、中英混打關著時的 Shift＋字母等）由 App 自己插入，善解不在它們前面補空白。例如組字中按數字鍵盤的 3：「下午」先送出，再由 App 插入 `3`，結果是「下午3 點」。
    - 用滑鼠移動游標，殼收不到通知。之後如果沒有再開始一次組字就直接從預測列送出，p 可能是舊的。
    - 開頭判斷靠 App 回報的游標前文字。回報不可靠的 App（研究紀錄 2026-10-06 提到的 VS Code、Chrome 等）可能多一個或少一個開頭空白；實機驗收要涵蓋這兩個。
- **關閉時**：`insertText` 收到的字串和 `o.commit` 逐字相同，和現在一樣。

## 2. 設定與介面

- `SpacingStore`（`var spacing: Bool?`，nil 表示沒設過，當作關），照 `AbbreviationStore` 的做法：
  - `MemorySpacingStore` 給 Kit 與測試用。
  - `DefaultsSpacingStore` 只在 `Shanjie` target，UserDefaults 鍵 `cjkSpacing`。
  - `Shell.init` 加這個參數，和其他 store 一樣**必填、沒有預設值**（修訂一：漏傳時要編不過，不能默默只存在記憶體裡）；`Shell.spacingOn` 加 setter，和其他開關一樣發設定改變的通知。
- 設定視窗：放在「選字」區塊，「英文的顯示」選擇器之後。
  - 開關文字「中英文之間自動加空格」。
  - 下一行說明（`.font(.caption)`，和中英混打的說明同樣式）：「在漢字和半形英文、數字之間自動加一個空格（俗稱「盤古之白」）。只改善解送出的文字。」
  - 不受中英混打開關或排列影響，永遠可以操作（ABC 打的英文、數字列打的數字都會用到）。
- 輸入法選單不加這一項，只在設定視窗。

## 3. 驗收

- **單元測試**（`macos/Tests/ShanjieKitTests`）：
  - 純函式 `CJKSpacing.apply(previous: Character?, text: String) -> String` 的表格測試，至少涵蓋：
    - 上面 §1 的每個例子。
    - p 是英文字母、數字、漢字、空白、全形標點、無，各一個。
    - 補充平面的漢字（例如 U+20000）兩邊。
    - 只有標點的送出。
    - 空字串。
  - Shell／Session 測試：
    - 開關關著時 `insertText` 收到的字串等於 `o.commit`（現有測試照舊通過）。
    - 開著時送出加了空白。
    - 同一個組字分兩次送出時，第二次的開頭依第一次送出的最後一個字元判斷。
    - 學習暫停時不補開頭空白，但送出文字裡面照樣加。
    - store 沒設過時是關。
    - （修訂一）組字開始的鍵帶修飾鍵（例如 Ctrl+\）時，上一個組字留下的 p 已經清掉，不補開頭空白。
    - （修訂一）送出後、核心回「不處理」的直通鍵之後再從預測列送出，不補開頭空白。
    - （修訂一）送出後直接從預測列送出，依上一次送出的最後一個字補開頭空白。
    - （修訂一）帶異體字選擇符的漢字（例如 U+845B U+E0100）和半形英數相鄰時加空白，當作 p 時也算漢字。
    - （修訂一）`SettingsModel` 讀到 `Shell.spacingOn`、`setSpacing` 會改到 `Shell`；說明文字等於契約 §2 那一行。
  - 突變（每一項都要讓某個測試失敗；build error 不算）：
    - 拿掉開頭的判斷。
    - 拿掉數字。
    - 標點旁邊也加。
    - 關著時也加。
    - 部分送出後不更新 p。
    - （修訂一）組字開始時不清 p。
    - （修訂一）直通鍵不清 p。
    - （修訂一）漢字判斷改回「整個字只有一個 scalar」。
  - 突變的結果（每一項由哪個測試抓到）寫進研究紀錄，不只留在 commit 或 PR 留言。
- `make test-swift` 通過；core 沒改。
- **實機**（維護者，備忘錄，開關打開）：
  1. 中英混打打「我用claude寫」→ 送出「我用 claude 寫」。
  2. 打「2026下午3點」→「2026 下午 3 點」。
  3. 用 ABC 打 `claude`，Caps Lock 切回善解打「寫」→「claude 寫」。
  4. 關掉開關重做 1 → 「我用claude寫」，沒有空白。
  5. （修訂一）在 Chrome 的文字欄位與 VS Code 的編輯器各做一次 3，看開頭空白是否正確；不正確就照 §5 停下來問。
